# 既有系统集成要求

2026-11-04。本文件记录后续业务集成的流程约束和待决建议，不是当前 CampusClaw 功能验收报告；其所述未来集成业务的实现和验收为 NOT_RUN。现有 Python 项目状态见[实现基线](../implementation-baseline.md)。

## 开发模式与既有规范的关系
组员在其有权修改的现有个人项目上扩展五模块，优先复用登录、角色、班级权限、数据库与AI/RAG，不要求重新建工程、重新实现已有能力、换技术栈、训练模型或拆微服务。API、表结构、代码组织由开发组员决定并记录；业务行为必须满足详细需求和验收场景。
此前不修改旧CampusClaw是保护组长个人项目，不禁止组员扩展自己的项目。不得未经授权修改组长旧项目，不假定该项目部署可用。后续业务集成以本文为准，早期功能说明中独立RAG服务和Go/React/MySQL为建议，不强制采用。RAG可以复用已有授权服务层，不要求远程独立服务；仍必须可信班级过滤、引用核对和失败处理。
历史骨架 OpenSpec 保持原样，仅记录当时的 Go/React/MySQL 骨架规划，不据此重建现有项目。工程规范的分层、授权、事务、日志、测试原则继续适用；骨架方案中的具体 Go 命令/目录/Compose 服务不约束当前 Python 实现。未来业务变更应登记现有技术栈的等价检查方式。

## 分工、实施和交付
1. A先盘点现有登录、角色/多班映射、数据库、RAG证据格式和运行方式，列已有/需适配/缺失；组长确认范围，B确认测试入口。
2. A为每个后续独立功能变更登记API操作、输入限制、错误映射、版本及幂等协议、数据迁移和运行方法，供B直接测试。建议顺序：广场→教师/AI→FAQ/统计；不向骨架tasks追加业务任务。
3. 保留原业务；A列原登录/核心业务/RAG回归清单，B修改前记录基线、修改后复跑。迁移不清空原库，失败可恢复；测试数据与原使用数据隔离。
4. 完整演示：学生提问→AI有据/无据→转人工→教师回复采纳→确认FAQ→检索引用→统计；另演示跨班拒绝和FAQ撤销。不能只展示静态页面或假响应。
5. 交付到约定小组仓库或评审分支：功能代码、必要基础依赖/精确版本、迁移、脱敏.env.example、启动/测试说明和证据。不得只留个人电脑、只交截图或依赖别人不可访问的私有路径。A负责实现说明，B负责独立clone启动/测试并审A代码，A交叉审B测试，组长审业务口径。提交/push按组长授权。

## 统计口径补充
数量默认[as_of-30天,as_of)，按问题创建时间过滤，状态是as_of时当前状态，不提供历史状态回放。建议允许自定义时间窗最大366天，起点<终点≤当前时间。pending/resolved/closed_unresolved互斥，和为total；故障不是0。
热门只按回复时间[as_of-7天,as_of)，左含右不含；人类每条实际回复计1，含关闭问题，不计AI。回复数、问题创建时间、ID依次降序取前10，计数为0不入榜。两种窗口在界面分别标注，每响应有as_of，最大30秒缓存且按班分键。

## 待开发组员确认
以下均为本组建议，待确认，并在对应change开始前冻结：现有角色/多班支持与适配缺口；AI证据是否含可验证文档/chunk/版本、8秒预算；幂等24小时及版本协议；FAQ三次重试和人工重试入口；既有栈对应检查命令；代码交付分支、可访问依赖、迁移/回退与原业务回归范围。
不得因技术差异自行改变教师采纳、关闭终态、跨班隔离和统计定义。只补业务闭环必要缺口，不增加注册管理、附件、成绩、通知、复杂调度平台。
