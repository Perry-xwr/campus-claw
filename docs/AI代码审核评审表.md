### 高风险场景专项核查记录

> **不允许跳过**：并发 / 事务 / 权限 / 数据一致性 四节必须逐节填写，缺任一节本评审表无效。

#### 并发
- 查了什么：逐行读 `campusclaw/retrieval_db.py:101-128` 的 `enqueue()`。`index_jobs` 建表（`retrieval_db.py:56-66`）只有 `status CHECK` 与 `idx_index_jobs_status(status,id)` 索引，**没有**保证「一材料同时最多一个 queued/running 任务」的 `UNIQUE` 约束或部分唯一索引。`enqueue()` 的这一不变量完全靠 `SELECT id ... WHERE material_id=? AND status IN ('queued','running')` 的**先查再写**维持——**这正是网页给的典型反例 `先 SELECT 1 ... 再 INSERT`**。如实记录：当前**没有**用唯一约束，不得写成已用。
- 依据哪条规约：七类清单第 3 类「唯一性是用数据库约束保证的，还是靠『先查一遍』？」；四步拆解法③④；`AGENTS.md` 第 4 节红线第 5 条、第 3.9 节反例。
- 结论：**不通过**。不变量未下沉到数据库，并发 / 多写入口下可能重复入队；须改为唯一索引 + 冲突按既定语义返回。

#### 事务
- 查了什么：`enqueue()` 用 `BEGIN IMMEDIATE` / `COMMIT` / 异常 `ROLLBACK`；`material_index` 的 `INSERT OR IGNORE` + `UPDATE` 与 `index_jobs` 的 `INSERT` 在同一事务内，无半提交。`busy` 命中时走 `ROLLBACK` 后返回，属读判定后回滚，未产生写入。
- 依据哪条规约：七类清单第 3 类「需要连续写多处的地方是不是放在同一个事务里？」；`AGENTS.md` 第 4 节红线第 4 条。
- 结论：**通过（保持）**。整改后仍须维持同一事务，冲突路径也要 `ROLLBACK` 干净后返回既有 `job_id`。

#### 权限
- 查了什么：`reindex_api()` 首行 `rc.require_write()`（认证 → 教师角色 → CSRF），随后 `materials.get_active_material(conn, id, int(user["class_id"]))`，跨班 / 不存在统一 `404 MATERIAL_NOT_FOUND`；未读取客户端 `class_id` / `role`。全仓无 `before_request`，该视图是自己显式加的校验。
- 依据哪条规约：`AGENTS.md` 第 4 节红线第 1、2、3 条；七类清单第 1 类「除了登录了没有，有没有检查这份数据属于当前用户？」。
- 结论：**通过**。无需修改。

#### 数据一致性
- 查了什么：`ensure_schema()` 的触发器 `queue_new_knowledge_entry` 也会 `INSERT INTO index_jobs`，与 `enqueue()` 写同一张表；两条写入路径都没有数据库级唯一约束兜底，重复任务只能靠 `index_status()` / worker 的状态判断消化。
- 依据哪条规约：七类清单第 3 类；`AGENTS.md` 第 4 节红线第 5 条。
- 结论：**不通过**。唯一索引须覆盖触发器与 `enqueue()` 两条路径，冲突语义统一。

### 三分法结论 + 对应后续动作

| 结论 | 判定标准 | 对应后续动作 |
| --- | --- | --- |
| `[ ] 可用` | 逻辑正确、符合规约与安全要求 | 补测试，交同学评审 |
| `[x] 待修改` | 方向对但有缺陷或偏离需求 | 列出具体修改项，改完重新审核 |
| `[ ] 风险无效` | 存在越权、数据错乱等风险或与需求无关 | 直接丢弃重写 |

判定理由：接口方向正确、权限链无误，但唯一性靠「先查有没有 busy 再插入」、没有数据库唯一约束，属网页典型反例；未达到「可用」，也不涉及越权 / 数据错乱到需丢弃重写，故为 `待修改`。

具体修改项：

1. 在 `ensure_schema()` 增加幂等的部分唯一索引，把不变量下沉到数据库：`CREATE UNIQUE INDEX IF NOT EXISTS uq_index_jobs_active ON index_jobs(material_id) WHERE status IN ('queued','running')`；该索引同时覆盖 `queue_new_knowledge_entry` 触发器与 `enqueue()` 两条写入路径。
2. 重写 `enqueue()`：去掉前置 `SELECT id ... busy` 的唯一性判断，改为直接 `INSERT INTO index_jobs`；捕获 `sqlite3.IntegrityError` 后按既定语义 `SELECT` 回既有 `job_id` 并返回（`ROLLBACK` 后返回，不新建、不吞掉异常）。写法见 `AGENTS.md` 第 3.9 节正例。
3. 保持 `BEGIN IMMEDIATE` 事务边界：`material_index` 的写入与 `index_jobs` 的 `INSERT` 仍在同一事务，冲突路径 `ROLLBACK` 干净；不得留半提交。
4. 补并发测试：两个并发 `POST /api/materials/<id>/reindex` 只产生一条 `queued` 任务，且第二次返回既有 `job_id`；测试通过后交同学评审。
5. 复核 `reindex_api()` 权限链（已核对，无需改动）：`require_write()` → `get_active_material(class_id)` → 统一 404。
6. 改完**重新审核**本表七个维度与高风险专项，结论改为「可用」后方可进入交叉评审与合入流程。
