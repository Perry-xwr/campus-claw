## 一、判定口径

两份课件的判据都不是「跑一遍工具」，所以先把口径固定下来，后面所有表格都按这个口径填。

### 1.1 两类用例验证两件事

| 类型 | 问的问题 | 走法 | 期望 |
| --- | --- | --- | --- |
| 功能用例 | 该做的做了吗 | 合法身份走正常路径 | 成功 |
| 反例用例 | 不该做的做不了吗 | **合法身份专走不该走的路** | 被拒绝 |

功能全绿对反例毫无证明力：授权判定缺失时，正常路径正常，越权路径也正常。这就是为什么第 9 课五条判据里有四条要用「已登录但想越权」的视角去测。

### 1.2 红与盲区不是一回事

- **红**：试过，防不住，有证据。
- **盲区**：没人试过，既不是红也不是绿。

注入类漏洞最常藏在盲区里——SQL / XSS / CSRF 在第 8 课属盲区（自查里没有这三条反例），第 9 课才补成常驻用例。安全边界的度量不是「跑了多少用例」，而是「反例覆盖了多少个能被外部触达的入口」。

### 1.3 修复的完成标志

不是「看起来好了」，而是**用与发现问题时完全相同的三段式（前置条件 / 操作 / 可观测结果）重放一遍变绿，且前后两个实际值都在案**。只写「已修复」的记录，别人无法复核。

本报告里每一条修复都按这个口径给前后两个值：SEC-06 的退出码从 1 到 0、SEC-07 的七列从空到有、DEF-01 的 `active_generation` 从 1 到 3。

### 1.4 敢交付与放心的两条判据

- 敢交付 = **任何人执行同一条命令，得到同样的绿**（证据在仓库里，不在某人的一次操作里）
- 放心 = **出问题能在用户发现之前看到**（指标、日志、追踪三根支柱）

第 10 课最后一条卡在第一条上的判据（「推送即构建」）本轮已补齐：推送后 GitHub Actions 连跑多次，run #9 十三个实质步骤全绿，第 12 步真的构建出镜像；验的是「换个人从仓库拉下来也能跑出同样的绿」，而不是「我本机能跑」。（另一条曾经卡在这里的「环境可复现」，已于本轮装上 Docker 后实跑补齐一半。）

### 3.2 两条红是怎么修的

修复前是 3 绿 2 红。这两条不是「写错了判据」，是实打实的缺口，因此按 1.3 的口径各给了前后的实际值。

#### SEC-06 依赖漏洞：从「未知」到「清零」

基线走的处置分支是「书面登记」，理由是当次环境未装审计工具、未联网比对，只能登记「未知」。本次装上 `pip-audit` 走 OSV 在线比对，立刻现形：

```
Found 4 known vulnerabilities in 2 packages
flask    3.1.1   PYSEC-2026-2151   → 3.1.3
werkzeug 3.1.8   PYSEC-2026-4312   → 3.1.9
AUDIT_EXIT=1
```

两个包都有现成补丁，本地 venv、`requirements.txt`、`pyproject.toml` 三处版本一致，全部受影响。升到 `Flask==3.1.3` / `Werkzeug==3.1.9` 并重解析锁文件后复测：

```
No known vulnerabilities found
AUDIT_EXIT=0
```

**退出码从 1 变 0**，这是修复的完成标志，不是「我升了版本」。原始输出 `reports/evidence/pip-audit-osv.log` 与 `reports/evidence/pip-audit-after.log`。

这一条顺带说明一件事：**「未知」和「0 高危」必须分开写**。第 8 课那份自查因为没比对工具而登记「未知」，读起来像通过，实际是把盲区当成了绿。

#### SEC-07 七列审计：从「缺两列」到「可回查」

课件要求一条记录独立回答七问：谁、何时、做了什么、对哪一条、结果如何、**用了哪个技能**、**花了多少**。原表只有前五问，且只记成功的工具调用，被拒绝的越权尝试一条不留。

三个层面一起补：

| 层 | 改动 |
| --- | --- |
| 表结构 | `mcp_tool_calls` 增 `action` / `object_id` / `skill_id` / `duration_ms` / `tokens` / `request_id` 六列，并做幂等增量迁移（老库自动 ALTER，不删数据） |
| 采集 | `_record()` 补技能标识；每次工具调用用单调时钟实测耗时；`request_id` 从请求上下文取 |
| 留痕 | 新增 `audit_events` 表，401 / 403 / 404 同样落一条；新增 `GET /api/audit/events`（仅教师、本班隔离） |
| 回查 | `scripts/audit_recheck.py` 按技能标识加时间窗回查，逐列断言，任一列空即退出码 1 |

真实跑一次技能调用取证（注册 MCP 服务器 → 连接发现工具 → 建技能绑定 `unit_convert@calc` → 学生提问 → 实际调用工具），回查结果：

| 列 | 取值 |
| --- | --- |
| 操作人 | `student_a1` |
| 操作时间 | `2026-11-12T02:01:52.222940+00:00` |
| 操作类型 | `skill.invoke` |

| 结果状态 | `ok` |

**关于 `tokens` 列**：MCP 工具调用不返回模型用量，该列在有值时记录、无值时留空。留空不是漏记，是无值可记——填 0 反而是伪造。

### 3.3 注入三件套：从盲区到常驻用例

| 类型 | 反例操作 | 实测 | 判定 |
| --- | --- | --- | --- |
| SQL 注入 | 检索词 `' OR '1'='1` | 400 `INVALID_QUERY`；前置对照：正常词命中 1 条 | 绿 |
| XSS | 标题存 img 标签形式的脚本 | 201 入库；页面源码中 img 标签以转义实体呈现，不含原始标签 | 绿 |

两条判定细节：SQL 注入必须先跑正常词做前置对照（功能整体坏掉时同样命中 0 条，会被误判为绿）；XSS 要看页面源码而不是看弹窗（不弹窗只是表象）。

### 4.3 判据 2：环境可复现（通过）

**已修的真问题一**：原 `uv.lock` 把每个包的 sdist/wheel 下载地址写死成清华镜像源（456 处 `files.pythonhosted.org` 被替换为镜像地址），换一台机器执行 `uv sync --locked`，**第一条命令就失败**。本次重解析锁文件，改为官方源。

这一条本身就是对「可复现」的反例：锁文件进了 Git，但锁的是别人机器上的镜像，等于没锁。

**已修的真问题二（DEF-04）**：`Dockerfile` 用 `python:3.12-slim`，而 `pyproject.toml` 声明 `requires-python = ">=3.11,<3.12"`。原注释写着「容器只读 requirements.txt，不受此处约束」——这句话技术上成立，但**本地验收跑 3.11、容器部署跑 3.12，被测对象与部署对象就不是同一个解释器版本**，一旦「本地绿、容器崩」，无从归因。已把镜像改为 `python:3.11-slim`。

| 接口 P95（毫秒） | `audit_events.duration_ms` 按桶取分位 | 61 个一分钟桶里 2 个有样本，其余留空 |
| 队列深度（条数） | `grade_tasks` 的入队 `+1` / 结束 `-1` 扫线 | 提交 4 个任务后尾部 **0 → 4**，消费者吃掉后回落 |

两个刻意的设计，都是为了不画出假绿：

* **错误率不互相平均**。课件专门写过「三个技能的错误率平均了就看不出哪一个在出问题」。按 `skill_id` 分线之后，一条技能全错也不会被另两条的正常拉平——上面那 0.5 就是三条线同时抬起来的样子，合计口径下只会显示一个 0.5 的「整体错误率」，看不出是全挂还是单个挂。
* **桶内样本不足留空**。零样本时 P95 恒为 0，画出来是「这一刻特别快」，实际是「这一刻没人用」。桶内少于 3 条就输出 `None`、不画点，和 `observability.py` 里「样本不足判跳过、不判通过」是同一条口径。

**时间轴缩放**四档：`1 小时 / 6 小时 / 今天 / 7 天`，对应桶宽 1 / 5 / 10 / 60 分钟，桶数都控制在 60 个上下——再多画在 190px 高的画布上就挤成一团。换档由**服务端按档位重新分桶**，不是前端把一分钟桶加总：**分位数不能相加**，四十个一分钟 P95 平均起来不是十分钟 P95。

画图用的是 canvas 手写折线（`campusclaw/templates/dashboard.html` 内联脚本），没有引任何第三方图表库——面板是内部巡检工具，为一个折线图多拉一个 CDN 依赖，等于把「面板能不能打开」绑在一个外部网络上。脚本单独用 `node --check` 过语法，再用假 canvas 上下文跑一遍取值断言（`lineTo` 被调 433 次、`stroke` 20 次），确认不是「页面能开但图画不出来」。

**红绿实验**：面板初始判定绿 → 手工把一条索引改成 `failed` → 判定转 `critical`、退出码 0 → 1 → 复原后回 0。只留一张绿的面板截图说明不了任何问题，退出码随数据状态翻转才是证据。

**追踪的必要性**：一次请求可能留下两类记录，分散在 `audit_events`（被拒绝的那段）与 `mcp_tool_calls`（技能被调用的那段）。只按时间倒序翻日志时，同一秒里混着别的请求，回答不了「这次操作到底发生了什么」。`request_id` 是唯一能把两段合成一条链的键，所以专门做了回查接口，并补了 6 条用例覆盖「能取回 / 顺序对 / 越权挡得住 / 查不到不编造 / 超长输入被挡」。

判通过，但边界要说清：**未接 OpenTelemetry，也没有 Prometheus / Grafana 实例**。自建面板能判读、能告警、能回查链路，但曲线留存、跨实例聚合、历史回溯这些要外部时序库才能做。判据问的是「出问题能不能在用户发现之前看到」，这一条现在答得上；问「能不能查三个月前的慢请求」，答不上。

还有一处是外部条件而非实现问题：课件原文写的是 `https://<部署域名>/claw/`，**这一半仍然只是本机实例**（`http://127.0.0.1:8110/claw/` 与局域网地址）。路径、权限、四条曲线都对得上，缺的是一台有公网域名的机器。这一条如实记进 4.8 的缺口表，不写成「已达标」。

## 五、验收过程中修复的缺陷

本轮除两条 SEC 判据，还修了一个阻断主链路的索引缺陷（DEF-01），并在补观测能力时
**又抓到两个自己写出来的缺陷**（DEF-02、DEF-03）。后两个值得单独写，因为它们都是
「功能看起来正常、判据表上是绿的」那一类——不主动去验取值，永远发现不了。

2026-11-13 补「换目录跑门禁」时，同一个病第四次发作：**DEF-10，空样本被判成绿，
还把仓库里的真证据覆盖成了空表**。这次不再靠「补个对象」绕过去，而是把「跳过」做成
独立状态——见本章末。

### DEF-01 索引失败后材料永久不可检索（已修）

**现象**：未配嵌入模型时，只要索引 worker 处理过某份材料并失败，这份材料此后检索不到，重启不自愈，调用重建接口仍失败。

**根因**：`index_worker` 失败时把 pending 切片标成 `failed` 但**不删除**，留下空壳；`tutor_db.backfill_keyword_ready` 的判据是「存在任意切片就跳过补建」，失败空壳恰好挡住了唯一的自愈路径。两条恢复路径同时断。

**修法与实测**：

| 改动 | 效果 |
| --- | --- |
| 补建判据改为「最新一代没有 ready 切片」 | 失败代会命中，触发重建 |
| `_write_keyword_chunks` 代次从硬编码 1 改为 `MAX+1` | 避免与既有代冲突，`active_generation` 能正确推进 |
| 写入时清理旧代失败空壳 | 库不随重建次数膨胀 |

实测 `material 3`：`active_generation` 由 **1 → 3**，第 2 代 3 条失败空壳被清理，最新代命中第二条 FAQ 正文。44 项验收由 42/44 转为 **44/44**，样例⑤「索引失败可重建」由部分通过转为通过。

### DEF-02 审计表 `actor_id` 恒为空（已修）

**现象**：审计事件里 `actor`（用户名）有值，`actor_id` 全是 NULL。表格看上去七列齐备，因为「列在不在」是齐全的。

**怎么发现的**：写追踪功能时链路一直取不到段，逐个字段打出来才看到 `_actor_snapshot()` 返回 `(None, 'teacher_a', 1)`——用户名和班级都对，只有 id 是空。

**根因**：`_actor_snapshot()` 取 `user["id"]`，而 `sessions.load_session_user()` 返回的键是 `user_id`（`id` 这个键在会话行里没被选出）。`KeyError` 被 `except (KeyError, TypeError, ValueError)` 吞掉，落到 `actor_id = None`。

这个坑的教训是**宽泛的 except 会把「字段名写错」伪装成「这个值本来就该空」**。审计写入是 best-effort 设计，异常一律吞，于是错误被永久静默。

**修法与实测**：

| 改动 | 效果 |
| --- | --- |
| 依次尝试 `user_id`、`id` 两个键 | 改名不再打穿；仍取不到才判空 |
| 回查脚本加断言「有用户名的记录必须带 actor_id」 | 只查列存在抓不到空值，必须查取值 |

红绿实验：手工插入一条 `actor='teacher_a' / actor_id=NULL` 的记录 → 断言「未通过（1 条 actor_id 为空）」，退出码 **1**；修复后真实越权请求落库 → 「通过（有用户名的记录均带 actor_id）」，退出码 **0**。

### DEF-03 零样本被判成绿（已修）

**现象**：门禁第 5 项的输出里，`http_p95_ms` 一行是「实际 0.0，阈值 500，结果 通过」。看起来指标健康，其实**一条请求都没采到**——零样本时 P95 恒为 0，必然小于任何阈值。

**根因**：`_check_latency` 在样本数低于 `p95_min_samples` 时返回 `ok=True` 并附一句提示。本意是「样本不足不下结论」，写法上却把「不判定」编码成了「通过」，面板和脚本都按绿展示。

**为什么必须改**：这正是本报告 1.2 节讲的「盲区不是绿」。面板上一条绿色的延迟指标，会让人以为延迟在正常范围内，而事实是没有任何证据。

**修法与实测**：

| 改动 | 效果 |
| --- | --- |
| 规则结果加 `skipped` 字段，与 `ok` 分离 | 「跳过」不再冒充「通过」 |
| 面板与脚本三态展示：通过 / 未通过 / 跳过 | 一眼看出哪条没证据 |
| `evaluate()` 单独统计 `skipped`，不计入 `passed` | 汇总数字不再虚高 |

实测三态：零样本 → `无样本 / 跳过`；注入 25 条 800ms 慢请求 → `800.0 / 未通过`（阈值 500）。规则确实随数据翻转，不是恒绿。

### DEF-05 索引失败后要重启才可检索（已修）

**现象**：容器里上传一份新材料，向量索引因缺嵌入模型失败，此时用 `keyword` 模式检索**一条都搜不到**；重启 app 后同样的检索立刻命中。

**根因**：`tutor_db.backfill_keyword_ready` 只在 `create_app` 里被调用一次。索引 worker 失败时把切片标成 `failed` 就把任务结束了，不再补建关键词就绪代次。于是「向量失败 → 关键词兜底」这条自愈路径**只存在于进程启动的那一瞬间**。长驻容器里，这个窗口等于「永远」。

DEF-01 修的是「失败代挡住了补建判据」，DEF-05 是它的下一层：判据改对了，但没有人在失败发生时去调用它。

**修法**：`campusclaw/index_worker.py` 在 `_mark_failed` 之后立即调用 `backfill_keyword_ready`，并包了 try——兜底失败不影响主循环。

**红绿实测**：

| 阶段 | 操作 | 结果 |
| --- | --- | --- |
| 红 | 旧镜像上传 `material_id=4`，等 12 秒，`keyword` 检索「独特词AAA917」 | 200，命中 **0** 条 |
| 绿 | 重建镜像后上传 `material_id=5`，第 6 秒检索「独特词BBB428」 | 200，命中 **2** 条，未重启 |

### DEF-06 Qdrant 客户端与服务端版本跨度过大（已修）

**现象**：worker 日志每次启动都有
`Qdrant client version 1.19.1 is incompatible with server version 1.15.5. Major versions should match and minor version difference must not exceed 1.`，
而 `docker-compose.yml` 把服务端钉在 `v1.15.5`、`requirements.txt` 把客户端钉在 `1.19.1`，两边差了 4 个小版本。

**为什么当时没修**：两条修法都需要验证——升镜像要先确认目标版本在仓库里可用，降客户端要先确认不引入新的依赖漏洞。排查当时容器到镜像仓库已不可达（连已存在的 `v1.15.5` 也拉不动），**拿不到验证条件就不动版本**。

**本轮修法**：镜像仓库仍不可达（`docker manifest inspect qdrant/qdrant:v1.19.1` 回 `Bad Gateway`），升服务端依旧没有验证条件；改从客户端侧收敛——`qdrant-client 1.19.1 → 1.15.1`，与服务端 1.15.5 同次版本，跨度归零，且不动镜像 tag、不触发向量数据迁移。改前先查两个版本在 OSV 上的已知漏洞（均为 0 条），排除「降版本换回漏洞」；`requirements.txt`、`pyproject.toml`、`uv.lock` 三处同步，`uv lock --check` 与 `uv sync --locked`（即 CI 的安装步）均通过。

**验证**：容器内把 `UserWarning` 提升为异常（最严格口径），实例化客户端不再抛告警；再做一次完整往返——建集合、建 `class_id` 的 payload 索引、写 2 个点、带 `class_id=7` 过滤的 `query_points`（2 点中只命中目标点，score 1.0）、按 id 删点、计数。覆盖的调用面正是 `retrieval.py` 与 `index_worker.py` 实际在用的那些。

| 项 | 修前 | 修后 |
| --- | --- | --- |
| 客户端版本 | 1.19.1 | **1.15.1** |
| 连接时告警 | `incompatible ... minor version difference must not exceed 1` | 无（即使把 `UserWarning` 提为异常） |
| 带过滤检索 | — | 2 点中按 `class_id=7` 命中 1 点，score 1.0 |
| 静态门禁 | 无此项 | `qdrant.version` 红 → 绿 |

**加了一道闸**：把「客户端版本 vs 服务端镜像 tag」做成静态校验的第 11 项，判据与客户端自身一致（主版本相同、次版本差 ≤1）。红侧把 `requirements.txt` 指回 1.19.1，该项判红、退出码 1，提示「次版本相差 4（要求 ≤1）」；恢复后转绿。这样下次任一侧单独升级会被静态挡下，而不是等运行期打告警。

### DEF-07 `make check-compose` 目标被写坏（已修）

**现象**：`Makefile` 第 40 行是

```
check-compose:/n/t$(PYTHON) scripts/check_compose.py --out $(EVIDENCE)/compose-static.json
```

本该是「换行 + 制表符」，实际存成了字面量 `/n/t`。make 会把 `/n/t$(PYTHON)` 当成前置依赖，`make check-compose` 与聚合目标 `make check` 都会以「找不到目标」失败。

**为什么一直没被发现**：门禁有三套入口——`Makefile`、`scripts/check-all.ps1`、`.github/workflows/check.yml`。Windows 上实际用的是 ps1（直接调 `python scripts/check_compose.py`），CI 的 `check.yml` 又直接写 `uv run python ...`，**三条路没有一条真的走 `make`**。于是「文件头和 `help` 里都写着的本地入口」是坏的，只是没人用。

**修法**：补回换行与制表符，目标体与其他五项保持同格式。

**教训**：入口不唯一的代价就在这里——只要某一套没人跑，它就会烂在那里，而且烂了半年也无人报错。真正该收敛的不是这一行，而是「到底以哪一套为准」，其余两套作为薄封装。

### DEF-08 门禁脚本依赖的 PyYAML 只是传递依赖（已修）

`scripts/check_compose.py` 直接 `import yaml` 解析 `docker-compose.yml`，但 `pyproject.toml` 与 `requirements.txt` 都没有声明 PyYAML——它能跑，是因为别的包顺带把它装了进来（`uv.lock` 里只是某包的依赖项，不是直接依赖）。传递依赖随时可能被上游去掉，一旦断掉，CI 第 6 步会红，而报错是「无法解析 compose：缺 pyyaml」，与真正的配置错误混在一起，归因成本很高。

**修法**：在 `pyproject.toml` 新增 `[dependency-groups] dev = ["PyYAML==6.0.3"]`。只进开发环境与 CI，不进运行时镜像（`requirements.txt` 保持不含它）。`uv lock` 后包数仍是 75，`uv sync --locked` 通过。

### DEF-09 CI 上的审计断言与观测规则是空转（已修）

**现象**：run #1 六步全绿，但「SEC-07 审计七列结构断言」「第 10 课运行观测告警判定」分别只用了不到 1 秒和 1 秒，比同批其他步骤都快得反常。

**根因**：`.gitignore` 第 18、20 行排除了 `data/` 与 `*.db`，仓库里没有数据库。干净 runner 检出代码后 `data/app.db` 不存在，而两个脚本都对「库不存在」直接返回成功：

| 脚本 | 库不存在时的行为 | 后果 |
| --- | --- | --- |
| `audit_recheck.py --allow-empty` | 打印「跳过回查」后 `return 0` | `assert_schema()` 未执行，七列一条没查 |
| `check_observe.py` | 打印「跳过告警判定」后 `return 0` | `evaluate()` 未调用，5 条规则一条没算 |

`audit_recheck.py` 第 142 行的注释写着「结构断言留给首次启动后的运行」——设计上知道这里不查，但 CI 从来没有过「首次启动」。于是步骤名里写着的断言与判定，一次也没发生，却显示成功。

**红绿**（在空目录里复现 CI 状态）：

```
无库： audit_recheck → 「数据库不存在…跳过回查」   退出 0，无判定表
       check_observe → 「数据库不存在…跳过告警判定」 0 条规则

建库后：init_schema → 35 张表，mcp_tool_calls 15 列，必需表齐备
       audit_recheck → 输出七列判定表            判定：绿
       check_observe → 规则数 5，4 通过 1 跳过
```

**修法**：新增 `scripts/init_schema.py`，按应用启动时的同一套 `db.apply_schema` + 各模块 `ensure_schema` 建出结构，只建表不灌数据，建完校验必需表齐备、缺表即退出码 1；`check.yml` 在安装依赖后调用它。修后 run #2 全绿，证据产物 24,996 → 27,571 字节。

**为什么不在脚本里改成「库不存在就判红」**：那会让 CI 永远红，而 CI 本来就不该有运行时数据库。缺的不是判红开关，是可检查的对象。

**同类问题的第三次**：DEF-03 是「零样本被判成绿」（`skipped` 与 `ok` 不分），DEF-09 是「无对象被判成绿」。两次的共同点都是**判据的输入缺失时，代码选了最省事的分支**。这次在 CI 侧补了对象，但没有改 `return 0` 本身——本地无库跑门禁仍会得到退出码 0，这一条当时记为已知残留。

**该残留已于 2026-11-13 补掉，而且它比预想的更糟**：库存在但没有近期记录时，脚本不是「跳过」，而是**写出了一份自称七列齐备的绿报告**。见 DEF-10。

### DEF-10 空样本写出「绿：七列齐备」，还把真证据冲掉了（已修）

**现象**：2026-11-13 21:00 在主仓库跑门禁，六项全绿、退出码 0。但跑完后 `reports/audit-recheck.md`
从 229 行变成 33 行，里面写着：

```
- 技能调用记录：0 条，七列齐备 0 条
- 拒绝尝试记录：0 条
| `actor` | 操作人 | `None` | 缺 |     ← 七列全部标「缺」
...
**绿**：七列齐备，拒绝尝试有留痕，按技能标识加时间窗可回查。
```

**同一份报告的表格说七列全缺，判定说七列齐备。** 这不是排版矛盾，是两条不同的代码路径：
表格读 `calls[0]`（空字典，所以七行都是 `None`／`缺`），判定读的是 `failures` 列表是否为空。

**根因有两层**：

| 层 | 问题 | 后果 |
| --- | --- | --- |
| 判绿逻辑 | `--allow-empty` 下，`calls` 为空时不追加 failure；判定段只剩「有 failure → 红，否则 → 绿」两个分支 | 空样本落进「否则」，写出绿 |
| 时间窗 | 默认 `WINDOW_MINUTES = 120`，写死「最近 2 小时」 | 判据是「任选一次调用、**事后**回查」，隔一天再跑就一条都查不到——证据会自己过期 |

**二次伤害**：脚本每次运行都无条件覆盖输出文件。于是一次空跑把仓库里那份**8 条调用、27 条拒绝、
229 行**的真实回查证据替换成了空表（`git diff` 是 −222 行）。这类损失不会报错，只会让证据悄悄消失。

**三次伤害**：报告里写进了绝对路径 ``D:\campus-claw\data\app.db``；`reports/evidence/observe.json`
的 `source` 同样变成绝对路径。换台机器复核时对不上，也把本机盘符带进了版本库。

**红绿**（三条分支，实测退出码）：

| 场景 | 命令 | 判定 | 退出码 | 是否写文件 |
| --- | --- | --- | --- | --- |
| A 无样本 + 放行（门禁默认路径） | `--db data/app.db --allow-empty` | 跳过（无样本） | **0** | **不写**（保留上一份有数据的记录） |
| B 有样本 | `--db data/app.db`（默认不限窗口） | 绿（8 条、七列齐备 8 条） | **0** | 写 |
| C 无样本 + 不放行 | `--window-minutes 1` | 红（两条原因：无调用、`audit_events` 为空） | **1** | 写（红报告本身有用） |

**修法**：

1. 判定分三态：红 / 绿 / **跳过（无样本）**，跳过时明确写「本轮未验证七列齐备，不构成证据」。
2. 退出码约定 `75 = 跳过`；`check_all.py` 汇总表把它单列一栏，提示「跳过的项没有产出证据，不得在报告里计为通过」。
3. 跳过时**不覆盖**已有报告——干净环境跑一次门禁，不该销毁上一次真实回查的记录。
4. 默认时间窗改为**不限**（`--window-minutes 0`），报告增写「最近一条调用：`<时间>`（距今 N 天）」，让复核的人知道证据有多旧。
5. 报告与证据里的库路径改为相对项目根的 `data/app.db`。

**为什么不让空样本直接判红**：干净环境本来就还没有任何调用，判红会让 CI 永远红——与 DEF-09 同一条理由。
缺的不是「判红开关」，是**把「没验」和「验过且通过」分成两个状态**。

**这是同一类病的第四次**：DEF-03（零样本 vs ok 不分）、DEF-09（无对象 vs 通过不分）、
DEF-10（无样本 vs 绿不分）。三次都是「输入缺失 → 走最省事的分支 → 输出一个好看的结论」。
这次不再靠「补个对象」绕过去，而是把状态本身拆开：**跳过就是跳过，它不是绿的另一种写法**。

### DEF-11 无向量环境下，两处入口把可用的关键词路挡死（已修）

**发现场景**：不是测试报的，是**准备真实用户试用**时按「试用者会怎么操作」走一遍，走不通。

**现象一**：在没配 `EMBEDDING_*` 的机器上，`/knowledge` 页的「检索方式」下拉框**默认选中的是
「混合检索」**。试用者输入关键词、直接点检索 —— 必然拿到 503「检索服务暂不可用」红字。
同一时刻 `mode=keyword` 是 200 且能命中，说明**关键词路是好的，只是没被选中**。

**现象二**：`index_worker` 常驻模式（试用时用的就是这个，不是 `--once`）只输出
`Waiting for Qdrant before claiming index tasks`，无限循环，一次都不认领任务。
材料永远停在 `pending`，检索自然搜不到。

**根因同一个**：代码假设 Qdrant 与 embedding 一定存在。

- 界面把 `hybrid` 硬编码成第一项，没有问过服务端「你能不能混合检索」；
- `index_worker.run()` 里那段等 Qdrant 没有出口：

```python
if not once:
    while True:
        try:
            qdrant(config).get_collections()
            break
        except Exception:
            LOG.info("Waiting for Qdrant before claiming index tasks")
            time.sleep(interval)
```

关键反证：**降级逻辑本身是好的**。用 `--once` 跑同一条链路，会打出
`Index task 3 failed: ModelUnavailable` 紧接着 `Keyword fallback rebuilt 1 material(s)`，
`material_index` 变 `ready`，关键词检索命中 1 条。也就是说「向量失败 → 重建关键词」这条路
一直存在，只是**被入口的等待挡在外面，永远轮不到执行**。

**修法**：

1. `/knowledge` 路由把 `RetrievalConfig` 的 `embedding_ready` / `chat_ready` 传给模板；
   模板据此决定：不可用时首项是 `关键词`，`混合检索` / `向量` 带 `disabled` 并注明
   「未配置向量服务」，页面加一行「关键词检索不受影响，已默认选中」，
   `生成简短回答` 一并禁用。
2. `index_worker.run()` 的等待条件加上 `config.embedding_ready`：为假时不进等待，
   直接开始认领，让 `process_one` 走既有降级。

**红绿**（同一套环境：无 Qdrant、无 `EMBEDDING_*`）：

| 场景 | 修复前 | 修复后 |
| --- | --- | --- |
| `/knowledge` 首项 | `hybrid`（点了 503） | `keyword`，另两项 `disabled` |
| 上传 → 索引 | 材料停在 `pending`，永不完成 | 2s `pending` → **6s `ready`** |
| 学生关键词检索 | 界面上无从得到（默认模式 503） | **200，命中 1 条，正是那篇** |
| 常驻 worker 日志 | 只打 `Waiting for Qdrant…` 死循环 | 打 `Embedding not configured; claiming tasks without waiting for Qdrant`，随后正常认领 |
| 门禁六项 | — | **6/6 通过，退出码 0**（改完复跑，未破坏其他项） |

**为什么不干脆让 `hybrid` 静默降级到 `keyword`**：那样界面上「混合检索不可用」这件事就消失了，
验收时说不清到底是真能混合检索还是偷偷换了条路。现在的做法是**如实：不支持的模式不给选、
选了仍 503，但默认值一定落在能用的那个上**——使用者不需要知道任何模式名字。

**分类**：前四次（DEF-03/09/10）是「输入缺失 → 最省事分支」，这一次不同，是
**「依赖缺失 → 入口假设它存在」**。共同点仍然是同一条：**代码在能力不足时没有把话说清楚**。

## 六、可复用的验收流程

### 6.1 执行顺序

```
1. 读规约      → 把验收样例逐条抄成断言，不凭印象
2. 定环境      → 独立数据目录，绝不碰项目 data/
3. 跑自带脚本  → 先确认「作者认为它能跑」，建立基线
4. 跑反例      → 补盲区：越权、注入、跨班、拒绝后副作用
5. 核数据库    → 断言库内事实与接口返回一致（统计恒等式、孤儿记录、跨班切片）
6. 做门禁实验  → 先红后绿，退出码必须随代码变化
7. 压测        → 同一脚本同一参数，两组数据，写清归因
8. 归档        → 原始 JSON + 可复跑脚本 + 命令
```

### 6.2 三条纪律

1. **不碰项目数据**：所有验收用 `CAMPUSCLAW_HOME` 指向临时目录，跑完删。
2. **不下「看起来对」的结论**：状态码、库内值、页面源码三处对齐才算证据。
3. **红要写清楚**：红在哪、复现步骤、根因代码位置、修法、修完的实测值。没有这些的红条目，别人无法复核。

## 八、结论

**第 9 课可以交差，而且是真修过的。** 五条判据全绿，其中两条原本是红：SEC-06 从「未知的高危」变成「4 条漏洞、升版本、复测退出码 1→0」；SEC-07 从「缺两列」变成「七列齐备 + 拒绝留痕 + 回查脚本进门槛」。注入三件套从盲区补成绿，证明三类注入在三个正确位置上被挡住（参数化查询、模板转义、一次性令牌），而不是靠某个过滤函数。

**第 10 课现在是 5 通过 / 1 部分 / 0 未执行。** 四次口径变更都记在 4.1 的表里，没有覆盖前一次，读的人能看到「哪条从部分转成了通过、凭什么转的、哪条又退回去了」。判据 6 这一格是「部分」而不是「通过」：3 名使用者各自登录走通了链路，但第 4 步跨班验证 0 人做到——补一次 30 秒就能转，没补之前不写通过。

转绿的五条各自靠什么转：

| 判据 | 上一轮卡点 | 本轮补的东西 |
| --- | --- | --- |
| 2 环境可复现 | 换干净目录跑不通门禁（缺 `.env`、本机无 `make`、到官方 PyPI 超时） | 干净目录补 `.env` 后四服务全起、空库自初始化、预置账号可登录；依赖改从清华镜像装（3 分 8 秒）；门禁入口收敛到 `scripts/check_all.py`，在全新 venv 里跑出 **5 通过 + 1 跳过 + 0 未通过、退出码 0** |
| 3 推送即构建 | 不产镜像 | 工作流加了 `docker build -t campusclaw:${GITHUB_SHA}`，`revision` 标签与提交 SHA 做断言（run #9 第 12 步，78 秒，497.9 MB），并在本机复现同一条命令 |
| 4 运行观测 | 无曲线、无技能维度、非 `/claw/` | `/claw/` 为主路径、四条曲线按技能分线、四档时间轴由服务端重新分桶 |
| 5 压测 | 改进项不是缓存或索引 | 加了检索缓存（TTL + LRU + 班级版本号），同一脚本两轮：`/api/search` +49.2% RPS、P95 −34.5%、错误率均 0% |
| 轻量端（判据 4 附项） | 没有手机端 | `/m` 单文件 H5，四步走查全绿、CORS 白名单实测 |

仍差的是判据 6 的最后一步：**3 人已到位（第 1–3 步有两人走通），第 4 步跨班验证 0 人做到**，补一次约 30 秒即可转通过。判据 2 已转通过，但留一句字面口径：`make check` 这条命令本身没敲过（本机没有 GNU make），跑的是 `Makefile` 里 `check:` 目标唯一的一行 `python scripts/check_all.py`；若验收要求「必须字面执行 make」，这一条退回部分通过（见 4.3）。

这个口径比上一版严：第一版按「做过就没有空白」给绿，第二版改成按课件判据原文逐字对照（1/4/1），此后两轮把可补的补上（4/1/1 → 5/0/1）。**每次变化都不是重新解释判据**——第一版的三条绿里，有两条其实是「有配置」而不是「条件全部满足」；后来的每一条绿都是补了实现再测的，每一处都能指到文件与实测数字。

四条里最有价值的是**缓存那一条**，因为它不是加个开关就完事：写入侧 `materials.py`（上传 / 改名 / 删除三处）与 `index_worker` 提交后都要失效，失效范围按班级而不是全局，否则 A 班一改材料、B 班的缓存连带清空。用班级维度递增的版本号做 key（`_EPOCH[class_id]`），失效是 O(1)、不需要遍历，也不需要维护条目清单。**空结果不缓存**——索引还没就绪时检索为空，把空缓存下来等于把一次临时故障固化 60 秒。命中率 99.95%（5,548/3）看着像刷出来的，其实是压测的重复查询太集中，这一点写进了 `reports/bench.md` 的「不能说明什么」。

「推送即构建」补得更曲折：run #1 一次就绿，但绿得可疑——三步只用了 1 秒。查下去发现 CI 上没有数据库，审计七列断言与观测 5 条规则**一条都没跑**（DEF-09）。加了建库步之后 run #2 再跑一次，产物从 24,996 涨到 27,571 字节，那两步才真的产出了判定表。**这条判据最终给绿，依据是 run #2 不是 run #1**——如果只看「第一次推就绿了」就收工，留下的是一份从没执行过断言的验收报告。

压测那一轮差点白跑：第一次跑出 15,568 个 500、`/api/conversations` 全 500，日志是 `database disk image is malformed`。根因不是代码，是反复硬杀服务进程，写事务在提交中途被终止。修法是给压测服务器加 `create_server()` + `close()` 到点优雅关闭，两轮各用独立数据目录副本，改完两个库 `integrity_check` 均 `ok`。**先证明数据是真的，再谈前后对比**——这条顺序比任何一个百分比都重要。

本轮同时按课件规定的固定文件名补齐了归档：`report.md`（根目录）、`reports/boot-reproduce.md`、`reports/pipeline.md`、`reports/observe-alert.md`、`reports/bench.md`、`reports/h5-lightweight.md`、`reports/feedback.md`、`reports/sec08-experiment.md`，并重写了 `reports/gate-red-green.md`（六项门禁 + 修复提交）。课件写的是「打不开即无法复核」，路径与文件名本身就是验收材料的一部分。

**还剩的三件事**：判据 6 的第 4 步补测（30 秒，人手现成）、SEC-08 前三步（需配 `CHAT_*` / `EMBEDDING_*`）、公网域名与告警外发通道（外部条件，非代码可补）。逐项写在根目录 `report.md` 第三节与本文 4.8。

**这一轮另外了结五个缺陷**：DEF-06（Qdrant 版本跨度，客户端 1.19.1 → 1.15.1 并做成静态校验第 11 项）、DEF-07（`make check-compose` 目标被写成字面量 `/n/t`）、DEF-08（门禁脚本依赖的 PyYAML 只是传递依赖）、DEF-09（CI 上两步空转）、DEF-10（空样本被判成绿，且把已有证据覆盖成空表）。前三个不影响判据但会让人踩空，第四个直接影响判据 3 的成色，第五个影响所有「看起来很绿」的结论。

**一条方法论上的教训**：这些缺陷都不是测试报出来的，全是「看结果不对劲」追出来的——1 秒的依赖安装、`/n/t` 这种乱码、跨 4 个次版本的告警、退出码 0 但没有输出、面板能开但 canvas 里没画线。**门禁的退出码只说明它自己没崩，不说明它检查了什么**，所以每次都要看它「产出了什么」。DEF-03、DEF-09、DEF-10 是同一个病的三次发作：输入缺失时走最省事那个分支。前两次靠「补个对象」绕过去，第三次没绕——把「跳过」做成独立状态，汇总表里单列一栏。**跳过不是绿的另一种写法。**

这条教训还有一个更硬的推论：**报告本身也是可能被污染的证据**。DEF-10 那次，是先发现「`audit-recheck.md` 从 229 行变成 33 行」，才顺着查到判定逻辑。如果当时只看到「六项全绿、退出码 0」就收工，丢掉的是一份真实回查记录，而且不会报任何错。

**门禁入口已经收敛**：此前 `Makefile`、`check-all.ps1`、`check.yml` 三套并存，DEF-07 正是「三套没人全跑」的产物。现在六项的步骤名、参数、顺序只写在一处（`scripts/check_all.py`），`Makefile` 的 `check:` 与六个单项目标都改成一行转发（`--only`），失效的 `check-all.ps1` 已删除。**代价是造出一个新的依赖**：以后加检查项只改 `check_all.py`，别再往 Makefile 里抄一遍。

**不建议现在做的**：外部时序库（Prometheus/Grafana）。自建面板已经能判读、四条曲线有数据、告警规则做了红绿，但在没有稳定长期部署之前，Grafana 上的曲线也只是本地进程快照，不构成新的证据。同理，镜像推 GHCR 也没做——本轮验证的是「构建得出来且标签对得上」，推仓库属于发布流程，与判据 3 无关。
