## 一、判定口径

两份课件的判据都不是"跑一遍工具"，所以先把口径固定下来，后面所有表格都按这个口径填。

### 1.1 两类用例验证两件事

| 类型 | 问的问题 | 走法 | 期望 |
| --- | --- | --- | --- |
| 功能用例 | 该做的做了吗 | 合法身份走正常路径 | 成功 |
| 反例用例 | 不该做的做不了吗 | **合法身份专走不该走的路** | 被拒绝 |

功能全绿对反例毫无证明力：授权判定缺失时，正常路径正常，越权路径也正常。这就是为什么第 9 课的五条判据里有四条要用"已登录但想越权"的视角去测。

### 1.2 红与盲区不是一回事

- **红**：试过，防不住，有证据。
- **盲区**：没人试过，既不是红也不是绿。

注入类漏洞最常藏在盲区里——本次的 SQL / XSS / CSRF 三项在第 8 课属盲区，第 9 课才补成反例。安全边界的度量不是"跑了多少用例"，而是"反例覆盖了多少个能被外部触达的入口"。

### 1.3 修复的完成标志

不是"看起来好了"，而是**用与发现问题时完全相同的三段式（前置条件 / 操作 / 可观测结果）重放一遍变绿，且前后两个实际值都在案**。只写"已修复"的记录，别人无法复核。

### 1.4 敢交付与放心的两条判据

- 敢交付 = **任何人执行同一条命令，得到同样的绿**（证据在仓库里，不在某人的一次操作里）
- 放心 = **出问题能在用户发现之前看到**（指标、日志、追踪三根支柱）

## 三、第 9 课：安全检查与审计

### 3.1 五条验收判据

| # | 判据 | 操作 | 期望 | 实测 | 判定 |
| --- | --- | --- | --- | --- | --- |
| 1 | 学生改不了技能与提示词 | 学生令牌重放 `PUT /api/prompt`、`POST /api/skills`，随后查库 | 403 且数据无变化 | 403 / 403；`class_prompts` 正文未变；`class_skills` 仍 2 条 | **绿** |
| 2 | 学生取不到他班数据 | A1 访问 B 班讲义、跨班检索 | 404 或空结果 | 跨班 GET 404；跨班检索 0 条；**本班检索 1 条**（证明检索能力可用） | **绿** |
| 3 | 技能调用可回查七列 | 一次调用后回查日志 | 七列齐全 | 实际字段只有 9 个，**缺 技能标识 / 耗时 / 用量** | **红** |
| 4 | 资产类两项 | 密钥扫描 + 依赖审计 | 0 命中；高危清零或书面登记 | 密钥 **0 命中**（13 提交 / 53 产物 / 1 日志）；依赖 **2 个包 4 条 PYSEC 漏洞，均有修复版本，未升级也未登记** | **红** |
| 5 | 注入三件套有反例且为绿 | 执行 SQL / XSS / CSRF 三条反例 | 空结果 / 无脚本执行 / 请求被拒 | 8/8 断言全绿（详见 3.3） | **绿** |

本次两条红恰好在两个极端：一条是**没人试过的旧账**（SEC-07 日志列不全，第 8 课就红，一直没修），一条是**这次才第一次看清的真账**——第 8 课的 SEC-06 因为没装审计工具，只能登记"高危数量未知"，相当于把"不知道"记成了"没发现问题"；本次装上 `pip-audit` 做在线比对，直接查出 `flask 3.1.1` 与 `werkzeug 3.1.8` 各有一个已知漏洞，且**两个都有现成的修复版本**。

这正好印证第 9 课那句话：**红是明确的缺口，盲区是未知的缺口**。"未知"一旦被打开，往往就是红。也说明"没装的检查"不能算"通过了的检查"。

### 3.2 三类缺口的归类结果

| 缺口类别 | 对应条目 | 本次结论 | 缺口成因 |
| --- | --- | --- | --- |
| 授权判定 | SEC-01 ～ 04 | **全部绿，无退化** | 判定已落在数据访问层（查询带 `class_id` 条件），不是只拦在路由上 |
| 注入防护 | 无编号（第 8 课是盲区） | **补齐三条反例，全绿** | 参数化查询 + 模板自动转义 + 一次性令牌三处都在位 |
| 资产与日志 | SEC-05 / 06 / 07 | 密钥**绿**；依赖**红**、日志**红** | 密钥有扫描机制；依赖审计此前从未真正跑过，第一次跑就出结果；审计表建了但列不全，缺"技能标识/耗时/用量" |

授权这一类值得单独说一句：**判定放在哪一层决定了它能不能被绕过**。SEC-04 验证的正是"绕过技能路由直调底层写接口"，结果仍是 403，说明判定不在路由层而在数据访问层——这是对的写法。如果只在页面上隐藏按钮，换个 `curl` 就绕过去了。

### 3.3 注入三件套（本次新增，课件第③步）

三条反例按课件规定的 `apitest/cases/<接口路径>/<方法>` 结构常驻，随 `make check` 跑。

| 类型 | 用例位置 | 反例操作 | 实测 | 判定 |
| --- | --- | --- | --- | --- |
| SQL 注入 | `apitest/cases/api/search/POST.py` | 检索词提交 `' OR '1'='1` | **HTTP 400 `INVALID_QUERY`** | 绿 |
| XSS | `apitest/cases/api/materials/upload/POST.py` | 讲义标题提交 `img` 标签形式的脚本（`img src=x onerror=alert(...)`） | 入库 201；列表页源码中该标题**已转义为 HTML 实体**，无可执行标签 | 绿 |
| CSRF | `apitest/cases/api/prompt/PUT.py` | Cookie 会话不带 `X-CSRF-Token` 改提示词 | **403 `CSRF_INVALID`，正文未变**；补令牌后 200 且更新 | 绿 |

两条判定细节容易做错，写下来供后续复用：

1. **SQL 注入必须有前置对照**。只看到"注入串命中 0 条"就判绿是错的——检索功能整体坏掉时同样命中 0 条。所以先跑一条正常词确认命中 ≥ 1，再跑注入串。
2. **XSS 要看源码，不看弹窗**。过滤不彻底但恰好没触发时，"没弹窗"同样成立；只有源码里"已转义"才是判定。

CSRF 这一条还顺带验证了纵深防御的两道都在：`Set-Cookie` 带 `SameSite=Lax`（浏览器侧），服务端逐次校验一次性令牌（服务端侧）。而且"被拒请求无写入副作用"单独成了一条断言——403 之后正文必须一字未改，这比只看返回码严格。

### 3.4 门禁：先红后绿

| 次序 | 代码状态 | 退出码 | 用例结果 |
| --- | --- | --- | --- |
| ① 基线 | 未改动 | **0** | apitest 8/8 绿 |
| ② 必红 | 故意跳过 CSRF 校验 | **1** | apitest 6/8，CSRF 两条红 |
| ③ 还原 | `git checkout` | **0** | apitest 8/8 绿 |

只留一次"绿"说明不了问题——命令可能根本没在检查。三次退出码随代码状态变化，才证明门禁真的在执行判定。完整证据与 patch 见 `reports/gate-red-green.md`。

### 4.2 判据 1：一键测试与门禁（唯一实跑的）

**命令**：`make check` ≡ `pwsh -File scripts/check-all.ps1`（本机无 GNU make）

**覆盖面**：SEC-05 密钥扫描 + SEC-06 依赖基线 → 第 8 课三条异步判据 → 第 9 课注入三件套

**实测**：退出码 0，三项全过；异步判据 3/3 绿，反例套件 8/8 绿。

本次对门禁做了两处修正，都是真实缺陷：

1. **覆盖面缺口**：原 `check` 目标只含 security + async 两项，第 9 课要求的反例三件套不在门禁内，且 `apitest/` 目录根本不存在——`make check-apitest` 必然失败。已补齐套件并接进 `check`。
2. **Windows 入口中断**：`check-all.ps1` 在 Windows PowerShell 5.1 下跑到第二项就中断，退出码为空。成因是 `$ErrorActionPreference = "Stop"` 把原生命令写到 stderr 的 Flask 访问日志当成**终止错误**。PowerShell 7 下不出现，所以开发机器上看不见。已加一层 `Invoke-Check`，调用期间放宽、判定仍只看退出码。

**但与课件定义的"门禁"还差一步**：课件要求"挂进 CI 与主干保护、退出码非 0 就进不去"。现在只是脚本级门禁——靠人记得手动跑，忘了就形同虚设。

### 4.3 判据 2：环境可复现（配置核验，未实跑）

把课件的"可复现"拆成两个前提逐条核：

| 前提 | 核验结果 |
| --- | --- |
| 依赖版本锁定 | `requirements.txt` **10 项全部 `==` 固定**；`uv.lock` 存在 |
| 构建步骤写成文件 | `Dockerfile`（python:3.12-slim + gunicorn）+ `docker-compose.yml`（4 服务）齐全 |
| 配置外置 | `.env.example` 值全部留空；密钥经环境变量注入，镜像层不含密钥 |
| 服务健康 | `app` 有 healthcheck 打 `/health`；`worker` 依赖 `app` 的健康状态启动 |
| Qdrant 版本固定 | `qdrant/qdrant:v1.15.5`，数据卷 `qdrant_data` 持久化 |

**两个阻塞点**：

1. **本机无 Docker**，`docker compose up -d` 跑不了，等于这一条连一次"干净目录能起来"都没验证过。
2. **`uv.lock` 把源写死成清华镜像**，每个包的 `sdist` / `wheel` URL 都是 `mirrors.tuna.tsinghua.edu.cn`。换一台机器或换网络后执行 `uv sync --locked` 会直接失败——这恰好破坏了"同样的提交在任何机器上构建出等价产物"这个前提。本次验收安装依赖时就是绕开 `--locked` 才装上的。修法是把锁文件重新生成成不带镜像 URL 的版本，或改用 `UV_DEFAULT_INDEX` 而非写进锁文件。

### 4.4 判据 3：推送即构建（不具备条件）

仓库无任何 CI 配置。这意味着：

- 没有"push 触发构建"的链路；
- 镜像没有构建编号，**无法反查某次提交对应哪个产物**；
- "不可变制品"无从谈起——目前 `campusclaw:latest` 这个 tag 会被反复覆盖，同一个 tag 在不同时间指向不同内容。

补这一项需要在云端仓库建 workflow：`check` → `docker build` → 推送镜像并按提交号打 tag。这部分不在本机完成。

### 4.5 判据 4：运行观测（三支柱缺两根）

| 支柱 | 现状 |
| --- | --- |
| 日志 | **有**。审计表 `mcp_tool_calls` 已建立，但缺三列（SEC-07）；运行日志写入 `.run/logs/` |
| 指标 | **无**。没有 `/metrics`、没有 Prometheus、没有 Grafana |
| 追踪 | **无**。无请求标识贯穿、无链路追踪 |

课件要求的四项曲线（按技能调用量、每技能错误率、接口 P95、队列深度）现在**一条都画不出来**，原因不是没有面板，而是**没有指标出口**：`mcp_tool_calls` 缺耗时与用量两列，本身就是这些指标的原始数据源。这也解释了为什么 SEC-07 的红比看上去重要——它同时卡住了安全判据和观测判据。

队列深度倒是有数据基础（`index_jobs` 表按状态可数），缺的是暴露成指标。

### 4.6 判据 5：压测（未做，给出可执行方案）

未安装 k6，本次未做基线。补跑方案：

```bash
# 1) 基线：当前版本
k6 run --vus 20 --duration 60s bench.js

# 2) 优化：至少一项，候选为
#    a. 检索侧：knowledge_chunks_fts 已有，但 _row_hit 逐条回查可合并为单查询
#    b. 配置侧：class_prompts / class_skills 每次请求查库，可加进程内缓存
# 3) 复测：同一脚本同一参数再跑一次

```

判定要点是**同一脚本同一参数**，换了参数的前后对比不成立。

## 五、可复用的验收流程

把上面两章收成一条能重复走的流程，下次改动后照此执行即可。

### 5.1 执行顺序

| 阶段 | 动作 | 命令 | 产出 |
| --- | --- | --- | --- |
| ① 开跑前 | 确认代码版本与工作区干净 | `git rev-parse HEAD`、`git status --short` | 基线提交号写进报告 |
| ② 功能回归 | 跑既有验收，确认没被改动误伤 | `python scripts/acceptance_async.py --out reports/evidence/async-acceptance.json` | 3 条异步判据 |
| ③ 反例复测 | 注入三件套 + 七项安全 | `python apitest/run_all.py`、`python scripts/acceptance_security.py ...` | 8 条 + 7 条判据 |
| ④ 门禁 | 一键跑全量，记录退出码 | `pwsh -File scripts/check-all.ps1` | 退出码 + 日志 |
| ⑤ 归档 | 证据进 `reports/evidence/`，结论进 `reports/*.md` | — | 可当场打开的路径 |

### 5.2 三条纪律

1. **复测必须换回原用例**。换了用例或换了期望，绿就失去了与红的可比性。
2. **红的时候先怀疑修复的写法**。"功能红了说明判定写严了"多数不成立——常见原因是归属条件写错了位置或值（把班级写成了用户）。
3. **安全修复单独开提交**。提交信息写清依据哪一条 SEC 编号，这样修复本身也留下了可追溯记录，与审计日志是同一条思路。

### 5.3 本次用到的脚本

| 脚本 | 作用 | 备注 |
| --- | --- | --- |
| `apitest/run_all.py` | 反例套件入口，有红则退出码 1 | 自带隔离实例，不依赖外部服务 |
| `scripts/acceptance_security.py` | SEC-01～07 七项三段式复测 | 第 8 课既有的脚本，本次原样重放 |
| `scripts/acceptance_async.py` | 第 8 课三条异步判据 | 回归用 |
| `scripts/check_security.py` | 密钥扫描 + 依赖基线 | 退出码随命中数变化 |
| `scripts/check-all.ps1` | 一键门禁（Windows 入口） | 本次修复了 5.1 兼容性缺陷 |

## 八、结论

**第 9 课不能算通过，但两条红都说得清。** 五条判据三绿两红：一条是审计日志七列缺列，从第 8 课红到现在没动过；另一条是依赖漏洞——第 8 课因为没装审计工具，把"未知"记成了过关，本次装上 `pip-audit` 一做，`flask 3.1.1` 与 `werkzeug 3.1.8` 各有一条已知漏洞且都有补丁。这一条比它看上去重要：它说明**"没做的检查"和"通过的检查"在报告里长得一样，但性质完全不同**，前者只要补上工具就立刻现形。

真正的增量是注入三件套：SQL / XSS / CSRF 从盲区变成有反例、且全绿。它证明的是三类注入在三个**正确的位置**上被挡住了——参数化查询、模板转义、一次性令牌——而不是靠某个过滤函数。这条区别很关键：按内容过滤（比如屏蔽 `script` 字样）能被编码变换绕过，按位置防护才绕不过。

**第 10 课只完成了六分之一，且原因不是懒。** 一键测试这一条做了，还顺带修了两个阻断门禁的缺陷（PowerShell 5.1 下入口中断、反例套件缺失）。剩下五条卡在同一件事上：**没有 Docker 和 CI，就没有"可复现"和"可交付"的实物证据**。写报告时可以把这一点写成"未执行并注明条件"，但不能写成"已具备"——前者是事实，后者是谎话。

**下一步按成本排序**，前三件都很便宜：

1. **升两个补丁版本**（`Flask==3.1.3`、`Werkzeug==3.1.9`），改四行版本号，重跑 `make check` 即闭合 SEC-06；
2. **修 SEC-07 三列**（采集层、写入层、查询层各一处），一次改动同时点亮安全判据和观测判据；
3. **把 `check` 挂进 CI**，让门禁从"靠人记得跑"变成"跑不过就进不去"；
4. **重生成不带镜像 URL 的 `uv.lock`**，让"换机器能装上"重新成立。

压测与真实用户放在最后——它们回答的是"扛不扛得住"和"好不好用"，得先有能稳定部署的环境才有意义。没有 Docker 就谈 P95，量出来的只能是笔记本的性能。
