## 一、判定口径

两份课件的判据都不是「跑一遍工具」，所以先把口径固定下来，后面所有表格都按这个口径填。

### 1.1 两类用例验证两件事

| 类型 | 问的问题 | 走法 | 期望 |
| --- | --- | --- | --- |
| 功能用例 | 该做的做了吗 | 合法身份走正常路径 | 成功 |
| 反例用例 | 不该做的做不了吗 | **合法身份专走不该走的路** | 被拒绝 |

功能全绿对反例毫无证明力：授权判定缺失时，正常路径正常，越权路径也正常。这就是为什么第 9 课五条判据里有四条要用「已登录但想越权」的视角去测。

### 1.2 红与盲区不是一回事

- **红**：试过，防不住，有证据。
- **盲区**：没人试过，既不是红也不是绿。

注入类漏洞最常藏在盲区里——SQL / XSS / CSRF 在第 8 课属盲区（自查里没有这三条反例），第 9 课才补成常驻用例。安全边界的度量不是「跑了多少用例」，而是「反例覆盖了多少个能被外部触达的入口」。

### 1.3 修复的完成标志

不是「看起来好了」，而是**用与发现问题时完全相同的三段式（前置条件 / 操作 / 可观测结果）重放一遍变绿，且前后两个实际值都在案**。只写「已修复」的记录，别人无法复核。

本报告里每一条修复都按这个口径给前后两个值：SEC-06 的退出码从 1 到 0、SEC-07 的七列从空到有、DEF-01 的 `active_generation` 从 1 到 3。

### 1.4 敢交付与放心的两条判据

- 敢交付 = **任何人执行同一条命令，得到同样的绿**（证据在仓库里，不在某人的一次操作里）
- 放心 = **出问题能在用户发现之前看到**（指标、日志、追踪三根支柱）

第 10 课的两条「部分通过」正是卡在第一条上：命令写好了，但还没人在第二台机器/CI 上跑出过同样的绿。

### 3.2 两条红是怎么修的

修复前是 3 绿 2 红。这两条不是「写错了判据」，是实打实的缺口，因此按 1.3 的口径各给了前后的实际值。

#### SEC-06 依赖漏洞：从「未知」到「清零」

基线走的处置分支是「书面登记」，理由是当次环境未装审计工具、未联网比对，只能登记「未知」。本次装上 `pip-audit` 走 OSV 在线比对，立刻现形：

```
Found 4 known vulnerabilities in 2 packages
flask    3.1.1   PYSEC-2026-2151   → 3.1.3
werkzeug 3.1.8   PYSEC-2026-4312   → 3.1.9
AUDIT_EXIT=1
```

两个包都有现成补丁，本地 venv、`requirements.txt`、`pyproject.toml` 三处版本一致，全部受影响。升到 `Flask==3.1.3` / `Werkzeug==3.1.9` 并重解析锁文件后复测：

```
No known vulnerabilities found
AUDIT_EXIT=0
```

**退出码从 1 变 0**，这是修复的完成标志，不是「我升了版本」。原始输出 `reports/evidence/pip-audit-osv.log` 与 `reports/evidence/pip-audit-after.log`。

这一条顺带说明一件事：**「未知」和「0 高危」必须分开写**。第 8 课那份自查因为没比对工具而登记「未知」，读起来像通过，实际是把盲区当成了绿。

#### SEC-07 七列审计：从「缺两列」到「可回查」

课件要求一条记录独立回答七问：谁、何时、做了什么、对哪一条、结果如何、**用了哪个技能**、**花了多少**。原表只有前五问，且只记成功的工具调用，被拒绝的越权尝试一条不留。

三个层面一起补：

| 层 | 改动 |
| --- | --- |
| 表结构 | `mcp_tool_calls` 增 `action` / `object_id` / `skill_id` / `duration_ms` / `tokens` / `request_id` 六列，并做幂等增量迁移（老库自动 ALTER，不删数据） |
| 采集 | `_record()` 补技能标识；每次工具调用用单调时钟实测耗时；`request_id` 从请求上下文取 |
| 留痕 | 新增 `audit_events` 表，401 / 403 / 404 同样落一条；新增 `GET /api/audit/events`（仅教师、本班隔离） |
| 回查 | `scripts/audit_recheck.py` 按技能标识加时间窗回查，逐列断言，任一列空即退出码 1 |

真实跑一次技能调用取证（注册 MCP 服务器 → 连接发现工具 → 建技能绑定 `unit_convert@calc` → 学生提问 → 实际调用工具），回查结果：

| 列 | 取值 |
| --- | --- |
| 操作人 | `student_a1` |
| 操作时间 | `2026-11-12T02:01:52.222940+00:00` |
| 操作类型 | `skill.invoke` |
| 操作对象 | 会话 id |
| 结果状态 | `ok` |
| 技能标识 | `单位换算引导` |

拒绝尝试同样留痕，4 条实测：学生越权建技能 403、学生删材料 403、B 班教师读 A 班材料 404、未认证 401。

**关于 `tokens` 列**：MCP 工具调用不返回模型用量，该列在有值时记录、无值时留空。留空不是漏记，是无值可记——填 0 反而是伪造。

### 3.3 注入三件套：从盲区到常驻用例

| 类型 | 反例操作 | 实测 | 判定 |
| --- | --- | --- | --- |
| SQL 注入 | 检索词 `' OR '1'='1` | 400 `INVALID_QUERY`；前置对照：正常词命中 1 条 | 绿 |
| XSS | 标题存 img 标签形式的脚本 | 201 入库；页面源码含 `&lt;img`，无原始标签 | 绿 |

### 4.2 判据 1：一键测试（通过）

见 3.4。这一条的价值不在「有脚本」，而在**退出码随代码状态变化**。只留一次绿说明不了任何问题——命令可能根本没在检查。

### 4.3 判据 2：环境可复现（部分通过）

**已修的真问题**：原 `uv.lock` 把每个包的 sdist/wheel 下载地址写死成清华镜像源（456 处 `files.pythonhosted.org` 被替换为镜像地址），换一台机器执行 `uv sync --locked`，**第一条命令就失败**。本次重解析锁文件，改为官方源。

这一条本身就是对「可复现」的反例：锁文件进了 Git，但锁的是别人机器上的镜像，等于没锁。

**仍未验证的**：本机没有 Docker，`docker-compose.yml` 四个服务（app / worker / qdrant / mcp）、healthcheck、版本固定都写了，但**一次 `docker compose up -d` 都没跑过**。配置正确 ≠ 环境可复现，所以判「部分通过」。

### 4.4 判据 3：推送即构建（部分通过）

但**没有在一次真实推送中跑过**：本机无 `gh`、无远端写权限。因此只能说「配置就位」，不能说「验证通过」。主干分支保护也需要在仓库设置里手动开启，代码侧无法完成。

这一条刻意不给绿：**「文件写好了」和「跑绿过」是两件事**，前者是配置，后者才是证据。

### 4.5 判据 5：压测（通过）

没有 k6，用标准库写 `scripts/bench.py`（固定并发 + 固定时长，断开连接自动重建）。两组同机同参数（vus=20、60 秒）：

| 指标 | Flask 内置服务器 | waitress 16 线程 | 变化 |
| --- | ---: | ---: | --- |
| 吞吐（四端点均值） | 151.4 RPS | 498.9 RPS | ×3.3 |
| P95（四端点均值） | 208.5 ms | 46.8 ms | −77.5% |
| 错误率（四端点均值） | 11.4% | 0% | 归零 |

第一组出现的 `status=0` 全部是**连接层失败**，不是服务端 500：Flask 内置服务器按 HTTP/1.0 应答并回 `Connection: close`，客户端无法保持长连接，20 路并发持续 60 秒把 Windows 动态端口吃满。换成支持长连接的 waitress 后归零。

这组数据回答的是「部署方式对并发能力的影响」，不是「改了哪段业务代码」，报告中不作混淆。完整数据与复跑命令见 `reports/bench.md`。

## 五、验收过程中修复的缺陷

除两条 SEC 判据，本轮还修了一个阻断主链路的索引缺陷（前一轮验收留下的 DEF-01）。

### DEF-01 索引失败后材料永久不可检索（已修）

**现象**：未配嵌入模型时，只要索引 worker 处理过某份材料并失败，这份材料此后检索不到，重启不自愈，调用重建接口仍失败。

**根因**：`index_worker` 失败时把 pending 切片标成 `failed` 但**不删除**，留下空壳；`tutor_db.backfill_keyword_ready` 的判据是「存在任意切片就跳过补建」，失败空壳恰好挡住了唯一的自愈路径。两条恢复路径同时断。

**修法与实测**：

| 改动 | 效果 |
| --- | --- |
| 补建判据改为「最新一代没有 ready 切片」 | 失败代会命中，触发重建 |
| `_write_keyword_chunks` 代次从硬编码 1 改为 `MAX+1` | 避免与既有代冲突，`active_generation` 能正确推进 |
| 写入时清理旧代失败空壳 | 库不随重建次数膨胀 |

实测 `material 3`：`active_generation` 由 **1 → 3**，第 2 代 3 条失败空壳被清理，最新代命中第二条 FAQ 正文。44 项验收由 42/44 转为 **44/44**，样例⑤「索引失败可重建」由部分通过转为通过。

## 六、可复用的验收流程

### 6.1 执行顺序

```
1. 读规约      → 把验收样例逐条抄成断言，不凭印象
2. 定环境      → 独立数据目录，绝不碰项目 data/
3. 跑自带脚本  → 先确认「作者认为它能跑」，建立基线
4. 跑反例      → 补盲区：越权、注入、跨班、拒绝后副作用
5. 核数据库    → 断言库内事实与接口返回一致（统计恒等式、孤儿记录、跨班切片）
6. 做门禁实验  → 先红后绿，退出码必须随代码变化
7. 压测        → 同一脚本同一参数，两组数据，写清归因
8. 归档        → 原始 JSON + 可复跑脚本 + 命令
```

### 6.2 三条纪律

1. **不碰项目数据**：所有验收用 `CAMPUSCLAW_HOME` 指向临时目录，跑完删。
2. **不下「看起来对」的结论**：状态码、库内值、页面源码三处对齐才算证据。
3. **红要写清楚**：红在哪、复现步骤、根因代码位置、修法、修完的实测值。没有这些的红条目，别人无法复核。

### 6.3 本次用到的脚本

| 脚本 | 作用 | 用法 |
| --- | --- | --- |
| `reports/verification/scripts/acceptance.py` | 44 项验收（正常/失败/越权 + 五个样例 + 数据库一致性） | `python reports/verification/scripts/acceptance.py` |
| `apitest/run_all.py` | 注入三件套，门禁用 | `python apitest/run_all.py --no-report` |
| `scripts/acceptance_security.py` | SEC-01～07 七项三段式复测 | `python scripts/acceptance_security.py --out reports/evidence/security-recheck-lesson9.json` |

## 八、结论

**第 9 课可以交差，而且是真修过的。** 五条判据全绿，其中两条原本是红：SEC-06 从「未知的高危」变成「4 条漏洞、升版本、复测退出码 1→0」；SEC-07 从「缺两列」变成「七列齐备 + 拒绝留痕 + 回查脚本进门槛」。注入三件套从盲区补成绿，证明三类注入在三个正确位置上被挡住（参数化查询、模板转义、一次性令牌），而不是靠某个过滤函数。

**第 10 课三条通过、两条部分、一条未做。** 通过的是能自己闭环的：门禁红绿、压测对照、指标出口。部分的两条卡在同一个前提上——**没有第二台机器/CI 跑过**，所以「可复现」与「推送即构建」只有配置没有证据。真实用户一条没有数据，不填。

**最该先做的两件事**（成本都很低）：

1. 推一次仓库，让 `.github/workflows/check.yml` 真跑一次，把运行页链接补进门禁文档——这一步同时把「部分通过」变成「通过」；
2. 装 Docker 跑 `docker compose up -d`，验证四容器编排与 healthcheck，补上「环境可复现」的另一半。

**不建议现在做的**：真实用户、面板与追踪。前者需要人，后者需要部署环境；在没有稳定部署之前，Grafana 上的曲线也只是本地进程的一次快照。
