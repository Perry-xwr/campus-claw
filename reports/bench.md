# 压测：同一脚本同一参数下的缓存改进前后对比（第 10 课）

> 判据原文：写入 `reports/bench.md`，同一脚本同一参数（k6，vus=20，60 秒）下的
> 优化前后 P95、吞吐、错误率，以及至少一项改进（**缓存或索引**）。
>
> 本轮改进项：**检索结果缓存**（`campusclaw/cache.py`）。
> 两轮走同一份代码、同一台机器、同一份数据目录的副本、同一批账号，
> 差别只有一个环境变量：`CAMPUSCLAW_RETRIEVAL_CACHE=0` 与不设。
>
> 原始数据：`reports/evidence/bench-before-cache.json`、`reports/evidence/bench-after-cache.json`。

## 一、结论先行

| 端点 | 轮次 | 请求数 | 吞吐 RPS | P50 (ms) | P95 (ms) | 错误率 |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `POST /api/search` | 改进前（缓存关） | 3,710 | **61.2** | 117.51 | **1431.32** | 0% |
| `POST /api/search` | 改进后（缓存开） | 5,551 | **91.3** | 59.28 | **937.35** | 0% |
| 变化 | — | +49% | **+49.2%** | **−49.5%** | **−34.5%** | 持平 0% |

其余三个端点（`/health`、`/api/materials`、`/api/conversations`）两轮数字在噪声范围内，
它们不经过检索链路，**没被改动也不该变**——这正是「改动只影响该影响的地方」的对照。

命中率：改进后一轮 `hits=5548 / misses=3`，**99.95%**（`GET /metrics` 的
`campusclaw_retrieval_cache_hits_total` 与 `_hit_rate`）。

**归因**：缓存省掉的是「同一 `(班级, 模式, 查询, 条数)` 的重复计算」——一次关键词检索要跑
FTS5 匹配 + 三个 JOIN，再对每个候选切片回查一次（N+1 查询，`limit×8=40` 个候选就是 41 条 SQL）。
同样的请求第二次起直接返回内存里的结果，所以 **P50 掉了近一半**。

## 二、为什么吞吐只涨 49%，不是几倍

因为瓶颈不在读，在写：

* `POST /api/search` 是**会改变状态的请求**（SEC-07 要求写请求留痕），每个请求都要
  往 `audit_events` 写一行并提交。
* SQLite 单写者 + 每次提交一次 fsync，本机实测每次提交约 10 毫秒 → 理论上限约 100 次/秒。
* 观察到的 91.3 RPS 正好压在这条线上；20 并发 × P50 59 毫秒按纯读算应该是 339 RPS，
  多出来的差距就是排队等提交。

所以这轮的改进是**真的**（同一请求的读开销被削掉），但不是「把系统压到新高度」——
天花板在审计写入，而削弱审计写入等于牺牲 SEC-07，不在这次改进范围内。
这条结论比「提升了几倍」有用：它指出了下一个该动的地方（审计批量提交或异步落盘），
也说明了为什么不再继续加缓存容量。

## 三、方法与可复现性

课件用 k6；本机没有 k6，也不该为压测引一个二进制依赖，因此用 `scripts/bench.py`
（纯标准库、固定并发、固定时长）做等价压测：参数口径与课件一致（**vus=20，60 秒**），
脚本入库、参数外置，别人照着能跑出同样的数字。

```bash
# 两轮各起一个干净实例（同一份数据目录副本，互不干扰）
CAMPUSCLAW_HOME=<数据目录A> CAMPUSCLAW_RETRIEVAL_CACHE=0 \
  python scripts/serve_waitress.py --port 8121 --seconds 340 &
python scripts/bench.py --base http://127.0.0.1:8121 --vus 20 --duration 60 \
  --out reports/evidence/bench-before-cache.json

CAMPUSCLAW_HOME=<数据目录B> \
  python scripts/serve_waitress.py --port 8122 --seconds 340 &
python scripts/bench.py --base http://127.0.0.1:8122 --vus 20 --duration 60 \
  --out reports/evidence/bench-after-cache.json
```

固定条件：同一台机器、waitress 16 线程（生产级 WSGI，不是 Flask 内置服务器）、
同一份演示数据的副本（2 份材料、2 个就绪切片）、同一批预置账号、同一台客户端。
`waitress` 只用于压测与验收，未进运行期依赖（生产用 gunicorn），安装方式：
`pip install waitress`。

## 四、缓存的三条边界（不是「加了缓存」一句话）

| 边界 | 做法 | 实测 |
| --- | --- | --- |
| 班级隔离 | 键 = `(class_id, 版本号, mode, query, limit)` | A 班账号查「示例讲义」得到 `A 班示例讲义`，B 班同词得到 `B 班示例讲义`，互不命中 |
| 写入即失效 | 材料上传 / 改名 / 删除 / 索引换代都调 `cache.invalidate_class()`，版本号 +1 | 写操作后同参数再查，结果随库变化，不返回旧标题 |
| 可关、可复现 | `CAMPUSCLAW_RETRIEVAL_CACHE=0` 关闭；TTL 60 秒兜底多进程 | 上面两轮就是用它开关跑出来的 |

另外**只缓存非空结果**：空结果常出现在材料刚上传、索引还没跑完的时刻，
缓存它会让「等一下再问」也一直是空的。

## 五、复盘：一次返工，500 全来自被杀坏的库

第一次跑改进前那轮时，`/api/search` 出现 15,568 个 500、`/api/conversations` 全部 500。
逐层排查：

1. 先看错误码分布：不是连接失败（`status=0`），是服务端 500；
2. 读服务端日志：`sqlite3.DatabaseError: database disk image is malformed`；
3. `PRAGMA integrity_check` → `Page 84: never used`，另一次重建时报
   `wrong # of entries in index idx_audit_events_status`；
4. 归因：压测前后反复起停服务时**直接结束进程**，写事务在提交中途被终止，
   库结构留下异常；异常库被下一轮压测读到，就成了满屏 500。

修法不是「重跑一次」：新增 `scripts/serve_waitress.py`，用
`waitress.create_server()` + `close()` 到点**优雅关闭**，两轮压测各用一个独立数据目录副本。
改完后两个库跑完 `integrity_check` 都是 `ok`，500 归零。

这件事与本轮改进无关，但它决定了两轮数字可不可信——**先证明数据是真的，再谈前后对比**。

## 六、附录：更早那组「开发服务器 vs waitress」基线

第一版压测拿 `python app.py`（Flask 内置服务器）跑，出现大量 `status=0`。核对后确认
**不是服务端错误**：同机单发与 5/10 路并发均 100% 200，瓶颈在内置服务器按 HTTP/1.0
应答并回 `Connection: close`，20 路并发 60 秒会把 Windows 动态端口吃进 TIME_WAIT。

| 指标 | 开发服务器 | waitress 16 线程 | 变化 |
| --- | ---: | ---: | --- |
| 吞吐（RPS，四端点均值） | 151.4 | 498.9 | ×3.3 |
| P95（四端点均值） | 208.5 ms | 46.8 ms | −77.5% |
| 错误率（四端点均值） | 11.4% | 0% | 归零 |

那组数据回答的是「部署方式对并发能力的影响」，不是「改了哪段业务代码」，
所以它只作为**背景**保留在这一节，判据 5 的前后对比以上面第一、二节为准。

## 七、这组数据不能说明什么

- **不能说明生产容量**：单机、单进程、本地回环，数据只有 2 份材料；真实部署有
  Nginx、多 worker、真实网络延迟与更大数据量。
- **不能说明长稳**：每轮只有 60 秒，没做 30 分钟以上的稳定性与内存观察；
  缓存是 LRU 上限 512 条，内存不会无限涨，但也没测过长时间下的淘汰行为。
- **不能说明写入路径**：压的全是读接口；写接口涉及 SQLite 写锁与索引入队，未测。
- **缓存收益依赖重复查询**：压测脚本每次发同一句查询，命中率 99.95% 是这种流量的上限；
  真实用户查询各不相同，命中率会低得多，收益也会小。这一点不能靠这组数字外推。
