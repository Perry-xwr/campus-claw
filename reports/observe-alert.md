# 观测面板与告警一次真触发 · 第 10 课 · 运行观测

> 课件第 10 课判据原文：打开 `https://<部署域名>/claw/` 下的监控面板，
> **按技能分线的调用量、每技能错误率、接口 P95 与队列深度各有曲线**。
> 证据文件名固定为 `reports/observe-alert.md`，内容判定是「面板路径、告警规则文本、
> 一次真触发的通知」三样齐。
>
> 本文件记录实测结果，**并逐条标注哪几项没达标**——不把「有面板」当成「面板达标」。

## 一、面板路径与权限

| 项 | 实测 |
| --- | --- |
| 教师面板 | `GET /dashboard` → **200**，30,332 字节 |
| 数据接口 | `GET /api/observability` → **200**（JSON，面板每 10 秒轮询一次：`setInterval(refresh, 10000)`） |
| 学生访问 | `GET /dashboard` → **302 → `/materials`**（被挡，不报错页面） |
| 未登录访问 | `GET /dashboard` → **302 → `/login`** |
| 追踪回查 | 面板内可按 `?request_id=` 输入追踪号，下钻单次请求（`audit_events` + `mcp_tool_calls` 按时间升序合成） |

**未达标项**：课件要求的路径是 `<部署域名>/claw/`。本项目当前路由为 `/dashboard`，
且没有部署域名（只在 `localhost:8080` 上跑）。—— 这是**路径与部署形态不达标**，
不是页面没做。

## 二、告警规则文本（5 条，阈值集中在 `campusclaw/observability.py`）

| 规则 ID | 级别 | 判定项 | 阈值 | 未通过的含义 |
| --- | --- | --- | --- | --- |
| `db_probe` | critical | 数据库可用 | `ok` | 库不可用时所有接口都会失败，先恢复服务 |
| `index_failed` | critical | 索引失败的材料数 | `0`（>0 即红） | 失败的材料对学生不可检索，检查 worker 与 embedding 配置 |
| `tasks_pending` | warning | 待处理任务数 | `50` | 积压持续上升说明 worker 跟不上或已停摆 |
| `http_p95_ms` | warning | 请求 P95 延迟（毫秒） | `500`，样本 <20 条时**跳过** | 先看哪条路径慢，再看是否缺索引或下游超时 |
| `audit_denials` | warning | 最近 60 分钟被拒绝请求数 | `200` | 突增可能是被扫描或被刷，到审计页按 status / actor 下钻 |

综合状态取最严重一档：有 `critical` 即 `critical`，否则有 `warning` 即 `degraded`，
全通过为 `ok`。**样本不足判「跳过」，不判「通过」**——零样本时 P95 恒为 0，
必然满足阈值，那是假绿（这是 DEF-03 的教训，已写进代码注释）。

## 三、一次真触发（不是只跑一次绿）

为了证明规则真的会红，在**数据库副本**上人为制造一条索引失败记录，前后各跑一次
`scripts/check_observe.py`（不动演示库，测完删除副本）：

### ① 触发前（基线）

```
规则数：5，未通过：0，跳过：1

规则                  判定项                         实际          阈值        结果
db_probe            数据库可用                       ok          ok        通过
index_failed        索引失败的材料数                    0           0         通过
tasks_pending       待处理任务数                      0           50        通过
http_p95_ms         请求 P95 延迟（毫秒）               无样本         500.0     跳过
audit_denials       最近 60 分钟被拒绝请求数              0           200       通过

综合状态：ok
判定：绿          退出码 0
```

### ② 写入一条 `status='failed'` 的 `material_index` 记录后

```
规则数：5，未通过：1，跳过：1

index_failed        索引失败的材料数                    1           0         未通过(critical)

综合状态：critical
退出码 1
```

同一条命令、同一份规则，仅因为库里多了一条失败记录，状态从 `ok` 翻到 `critical`、
退出码从 0 变 1。**这就是「规则真的在判定」的证据**，而不是「面板能打开」。

### ③ 线上实际状态（原库，未人为改动）

```
status: ok ｜ rule_count: 5 ｜ passed: 4 ｜ skipped: 1 ｜ alerts: []
```

## 四、与课件要求的逐条对照

| 课件要求 | 实际 | 判定 |
| --- | --- | --- |
| 面板路径 `<域名>/claw/` | `/dashboard`，无部署域名 | 不达标 |
| 按技能分线的调用量**曲线** | 暴露的指标键只有 `requests_total`、`requests_by_path`、`requests_by_status`、`duration_ms`；**没有按技能维度聚合**，面板无图表（`canvas`/`svg` 计数为 **0**，全是数字与表格） | 不达标 |
| 每技能错误率曲线 | 同上，无技能维度 | 不达标 |
| 接口 P95 曲线 | 有 P95 数值（含样本不足跳过），无曲线 | 部分 |
| 队列深度曲线 | 有 `tasks_pending` 数值，无曲线 | 部分 |
| 告警规则文本 | 5 条，阈值集中可调 | 达标 |
| 一次真触发 | 副本库制造 failed 记录 → `critical`，退出码 1 | 达标（但**不是**「通知」，见下） |

**关于「通知」**：课件写的是「一次真触发的通知」。当前实现是**面板内可见 +
CLI 判定退出码非 0**，没有接外部通知渠道（邮件/webhook/IM）。所以严格说，
「触发」做到了，「通知」没有做到——判据里这一条按**部分达标**记。

## 五、判定

运行观测的**数据与判定逻辑**是实的：三支柱齐（`/metrics` 指标、`audit_events` 日志、
`request_id` 追踪）、5 条规则可红可绿、退出码随数据变化。

**不达标的是呈现层**：面板没有曲线、指标没有按技能维度切分、路径不是 `/claw/`、
没有部署域名、告警没有外发通知。这些属于 B 档（需改代码与部署）的工作，
不在文档补齐范围内，此处如实留痕，不用「面板可判读」一句带过。
