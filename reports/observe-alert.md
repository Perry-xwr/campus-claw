# 观测面板与告警一次真触发 · 第 10 课 · 运行观测

> 课件第 10 课判据原文：打开 `https://<部署域名>/claw/` 下的监控面板，
> **按技能分线的调用量、每技能错误率、接口 P95 与队列深度各有曲线**。
> 证据文件名固定为 `reports/observe-alert.md`，内容判定是「面板路径、告警规则文本、
> 一次真触发的通知」三样齐。
>
> 本文件记录实测结果，**并逐条标注哪几项没达标**——不把「有面板」当成「面板达标」。

## 一、面板路径与权限（实测）

| 项 | 实测 |
| --- | --- |
| 教师面板（课件路径） | `GET /claw/` → **200**，45,662 字节，含 **3 个 `<canvas>`** |
| 兼容入口 | `GET /dashboard` → **200**，同一张面板（早期文档、截图与用例指向它） |
| 补斜杠 | `GET /claw` → **302 → `/claw/`**（保留查询串，`?request_id=` 不丢） |
| 数据接口 | `GET /api/observability` → **200**（面板每 10 秒轮询刷新数字） |
| 曲线接口 | `GET /api/observability/series?range=1h` → **200**（教师身份） |
| 学生访问 | `GET /claw/` → **302 → `/materials`**（被挡，不返回面板内容） |
| 未登录访问 | `GET /claw/` → **302 → `/login`** |
| 追踪回查 | 面板内按 `?request_id=` 输入追踪号，`audit_events` + `mcp_tool_calls` 按时间升序合成一条链 |

**已经做到的**：路径就是课件要求的 `/claw/`，且 `/dashboard` 不重定向、直接渲染同一张面板——
把旧链接改 302 只会让既有用例从「200」变成「302」，那是为了路径整齐去改判据，不是修问题。

**仍缺的**：没有公网域名，只有本机与局域网地址（`http://127.0.0.1:8110/claw/`、
`http://172.20.10.2:8110/claw/`）。判据里「`<部署域名>`」这一半仍是本机实例。

## 二、四条曲线分别是什么、怎么来的（实测）

面板上三张图四条线，**没有一条是前端造的假数据**：全部来自上一课补齐的审计七列。

| 曲线 | 数据来源 | 实测取值（`range=1h`） |
| --- | --- | --- |
| 技能调用量（按技能分线，不合计） | `mcp_tool_calls.skill_id` + `created_at` 分桶计数 | 3 条线：`公式加换算` 4 次、`公式提示` 2 次、`单位换算` 2 次 |
| 每技能错误率 | 同上，`status != 'ok'`（含 `denied` / `error`）除以总数 | 三条线在同一分钟桶各 **0.5**（故意断开 MCP 服务器一轮，6 次调用里 3 次 `denied`） |
| 接口 P95（毫秒） | `audit_events.duration_ms` 按桶取分位 | 61 个一分钟桶中 2 个有样本（桶内 <3 条留空，不画成 0） |
| 队列深度（条数） | `grade_tasks` 的入队 `+1` / 结束 `-1` 扫线 | 提交 4 个任务后 `queue` 尾部 **0 → 4**，消费者吃掉后回落 |

窗口内合计：**技能调用 8 次、失败 4 次**；`/api/observability` 返回的 5 条规则
`status=ok / passed=5 / skipped=0`。

**为什么错误率不「平均」**：课件专门写过「三个技能的错误率不互相平均，平均了就看不出
哪一个在出问题」。面板按 `skill_id` 分线，一条技能全错也不会被另两条的正常拉平。

**为什么桶内样本不足要留空**：零样本时 P95 恒为 0，画出来是「这一刻特别快」，
实际是「这一刻没人用」。这与 `observability.py` 里「样本不足判跳过、不判通过」是同一条口径。

## 三、时间轴缩放

面板右上角四档：`1 小时 / 6 小时 / 今天 / 7 天`，对应桶宽 1 / 5 / 10 / 60 分钟，
桶数都控制在 60 个上下——再多画在 190px 高的画布上就挤成一团。

换档位由**服务端按档位重新分桶**（`/api/observability/series?range=`），
不是前端把一分钟桶加总：分位数不能相加，四十个一分钟 P95 平均起来不是十分钟 P95。

## 四、告警规则文本（5 条，阈值集中在 `campusclaw/observability.py`）

| 规则 ID | 级别 | 判定项 | 阈值 | 未通过的含义 |
| --- | --- | --- | --- | --- |
| `db_probe` | critical | 数据库可用 | `ok` | 库不可用时所有接口都会失败，先恢复服务 |
| `index_failed` | critical | 索引失败的材料数 | `0`（>0 即红） | 失败的材料对学生不可检索，检查 worker 与 embedding 配置 |
| `tasks_pending` | warning | 待处理任务数 | `50` | 积压持续上升说明 worker 跟不上或已停摆 |
| `http_p95_ms` | warning | 请求 P95 延迟（毫秒） | `500`，样本 <20 条时**跳过** | 先看哪条路径慢，再看是否缺索引或下游超时 |
| `audit_denials` | warning | 最近 60 分钟被拒绝请求数 | `200` | 突增可能是被扫描或被刷，到审计页按 status / actor 下钻 |

综合状态取最严重一档：有 `critical` 即 `critical`，否则有 `warning` 即 `degraded`，
全通过为 `ok`。**样本不足判「跳过」，不判「通过」**——零样本时 P95 恒为 0，
必然满足阈值，那是假绿（这是 DEF-03 的教训，已写进代码注释）。

## 五、一次真触发（不是只跑一次绿）

为了证明规则真的会红，在**数据库副本**上人为制造一条索引失败记录，前后各跑一次
`scripts/check_observe.py`（不动演示库，测完删除副本）：

### ① 触发前（基线）

```
规则数：5，未通过：0，跳过：1

规则                  判定项                         实际          阈值        结果
db_probe            数据库可用                       ok          ok        通过
index_failed        索引失败的材料数                    0           0         通过
tasks_pending       待处理任务数                      0           50        通过
http_p95_ms         请求 P95 延迟（毫秒）               无样本         500.0     跳过
audit_denials       最近 60 分钟被拒绝请求数              0           200       通过

综合状态：ok
判定：绿          退出码 0
```

### ② 写入一条 `status='failed'` 的 `material_index` 记录后

```
规则数：5，未通过：1，跳过：1

index_failed        索引失败的材料数                    1           0         未通过(critical)

综合状态：critical
退出码 1
```

同一条命令、同一份规则，仅因为库里多了一条失败记录，状态从 `ok` 翻到 `critical`、
退出码从 0 变 1。**这就是「规则真的在判定」的证据**，而不是「面板能打开」。

### ③ 线上实际状态（原库，未人为改动）

```
status: ok ｜ rule_count: 5 ｜ passed: 5 ｜ skipped: 0 ｜ alerts: []
```

## 六、与课件要求的逐条对照

| 课件要求 | 实际 | 判定 |
| --- | --- | --- |
| 面板路径 `<域名>/claw/` | `GET /claw/` 200；无公网域名，本机与局域网可开 | **路径达标，域名未达标** |
| 按技能分线的调用量曲线 | 3 条线合计 8 次真实调用（`mcp_tool_calls` 落库） | 达标 |
| 每技能错误率曲线 | 三条线在故障那一分钟同为 0.5 | 达标 |
| 接口 P95 曲线 | 有样本的桶出点，无样本留空 | 达标（样本少时点稀疏） |
| 队列深度曲线 | 提交 4 个任务后 0 → 4 | 达标 |
| 时间轴缩放 | 1h / 6h / 24h / 7d，服务端重新分桶 | 达标 |
| 告警规则文本 | 5 条，阈值集中可调 | 达标 |
| 一次真触发 | 副本库制造 failed 记录 → `critical`，退出码 1 | 达标（**不是**「通知」，见下） |

**关于「通知」**：课件写的是「一次真触发的通知」。当前实现是**面板内可见 +
CLI 判定退出码非 0**，没有接外部通知渠道（邮件 / webhook / IM）。所以严格说，
「触发」做到了，「通知」没有做到——这一条按**部分**记，不写成「告警已闭环」。

## 七、复跑方式（三分钟）

```bash
# 1) 起主应用与内置 MCP 工具服务
python scripts/serve_waitress.py --port 8110 --seconds 600
cd mcp-server && MCP_AUTH_TOKEN=demo-token python -m mcp_server &   # 默认 8090

# 2) 造出按技能分线的真实调用（含一轮故意断开服务器，让错误率非零）
python scripts/skill_demo.py --base http://127.0.0.1:8110 \
  --mcp http://127.0.0.1:8090 --token demo-token --rounds 2 --fail round-1

# 3) 打开面板，切换四档时间轴
#    http://127.0.0.1:8110/claw/
```

## 八、判定

运行观测这一条**从「有面板无曲线」推进到「四条曲线各有数据」**：
路径 `/claw/`、按技能分线、错误率不平均、P95 与队列深度并排、四档时间轴。

仍然缺两样，都不打算用文字补：**公网部署域名**与**告警外发通知**。
前者要一台对外可达的机器与域名，后者要一个可用的通知渠道（邮件/IM/webhook）；
两者都属于外部条件，接入方式写在上面「关于通知」一段里。
