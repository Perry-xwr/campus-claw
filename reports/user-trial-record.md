## 怎么起服务、怎么给地址

### 一条命令

```bash
cd /d/campus-claw
.venv/Scripts/python.exe scripts/trial_start.py
```

它会做三件事，顺序是刻意的：**先查端口 → 再起服务 → 最后打一张信息卡**。

1. 端口被占就先停下来说清楚，不会假装起成功（8080 上挂着上一个实例是最常见的翻车方式）；
2. 监听 `0.0.0.0` 而不是 `127.0.0.1`——后者只有本机能连，给对方一定打不开；
3. 打完卡直接前台跑，`Ctrl+C` 或 `--seconds` 到时都走 waitress 的 `close()` 收尾。
   **不要直接关窗口硬杀**：写事务停在提交中途会损坏 SQLite，本项目已经因此坏过两个库
   （见 `reports/bench.md` 的返工复盘）。

只想看信息卡、不起来服务（服务已经在别处跑着时）：加 `--print-only`。
想开到某个时间自动收工（比如一小时）：加 `--seconds 3600`。

信息卡里已经包含地址、四个账号，以及一段可以直接复制转发的话。

### 地址是怎么来的

脚本会自己查，原理和手动查一样：

```powershell
# 先确认本机在这张网里的地址，不要照抄别人给的 IP
Get-NetIPAddress -AddressFamily IPv4 |
  Where-Object { $_.IPAddress -notlike '127.*' -and $_.IPAddress -notlike '169.254.*' } |
  Select-Object InterfaceAlias, IPAddress
```

对方访问 `http://<上一步查到的地址>:8080`。Windows 防火墙首次会弹窗，要选**允许专用网络**。

### 网络前提：必须和你在同一张网里

本轮实测本机出站地址是 `172.20.10.2`——**手机热点网段**（`172.20.10.0/28` 是 iOS 个人热点的固定分配）。
这意味着：

- 对方连**同一个热点**才打得开；换回自己的 Wi-Fi 就不通；
- 对方在宿舍自己的网络里，**不经过内网穿透或公网部署是访问不到的**；
- 热点下设备数有限（iOS 一般 5 台），一次不要同时叫太多人。

有两种可行的约法，选一种：

| 约法 | 怎么做 | 适合 |
| --- | --- | --- |
| 面对面 | 你开热点，对方连上，当场做完 | 最省事，卡了点能看到 |
| 同一 Wi-Fi | 都用同一个路由器（非热点），脚本自动查出该网段地址 | 对方在隔壁 |

不要在这一步含糊：地址给错了，对方打开是「无法访问此网站」，而他会以为自己操作错了——
这正是判据最怕的假信号。

### 对方说打不开：按这个顺序查

按顺序排除，**每一步都要看具体现象，不要跳到结论**。

| 顺序 | 查什么 | 怎么查 | 现象 → 处理 |
| --- | --- | --- | --- |
| 1 | 服务在不在 | 自己浏览器开 `http://127.0.0.1:8080` | 打不开 → 服务没起或崩了，回去看终端 |
| 2 | 端口对不对 | 脚本信息卡上的端口 | 用了 8121（压测端口）而不是 8080 → 给错地址 |
| 3 | 对方在同一张网吗 | 问对方连的是哪个 Wi-Fi / 热点 | 不同网 → 按上面的「两种可行约法」重约 |
| 4 | 地址抄对没 | 对照信息卡逐位念一遍 | 抄错一位 → 重发 |
| 5 | 防火墙 | 首次访问时 Windows 弹窗 | 点了「取消」→ 在「Windows Defender 防火墙 → 允许应用」里给 Python 开专用网络 |
| 6 | 浏览器 | 对方用的是什么浏览器 | 极旧 IE / 内嵌浏览器 → 换 Chrome 或 Edge |
| 7 | 账号 | 是不是 403 / 401 | 403 多半是用了学生账号做教师动作（**这是设计**，记观察点，不是故障）；401 是口令打错 |
| 8 | 检索报「检索服务暂不可用」 | 看页面「检索方式」选的是不是混合检索 | 是 → **当前环境的已知阻塞**，不是对方的问题。按上一节的 A/B 补齐；临时可用关键词模式继续，但要在记录里注明「本次用了关键词，混合检索未覆盖」 |

**第 7 条尤其要分清**：学生上传材料返回 403 是权限设计生效，不是 bug。同理第 4 个任务
（B 班搜 A 班材料搜不到）**搜不到才是对的**。试用者如果在这两处停下来问「为什么不行」，
那是一个很好的信号——说明隔离与权限是可感知的，记进「卡住的步骤」，不要当成失败。

### 2026-11-13 复测：两个会让任务 2/3 必卡的阻塞点

在**当前本机环境**（Docker 未启动、Qdrant 不可达、未配 `EMBEDDING_*`）重走了任务 2、3 的真实路径，
结果和上面那份预检不同，必须记下来：

| 步骤 | 实测 | 说明 |
| --- | --- | --- |
| 教师登录 | 200 | 正常 |
| 上传 `.md` | 201，`material_id=3`，状态 `active` | 正常 |
| 上传后立刻查索引 | `material_index` 无记录 | job 已入队，等 worker 处理 |
| 跑 `index_worker --once` | `Index task 3 failed: ModelUnavailable`，紧接着 `Keyword fallback rebuilt 1 material(s)`，`material_index` 变 `ready` | **降级机制生效**：向量建不出来，就只建关键词索引 |
| `POST /api/search` `mode=keyword` | **200，命中 1 条** | 关键词检索可用 |
| `POST /api/search` `mode=hybrid` | **503 `RETRIEVAL_UNAVAILABLE`** | 向量路失败即中断，不降级 |
| `POST /api/search` `mode=vector` | **503** | 同上 |
| 跑 `index_worker`（不带 `--once`，即试用时会用的常驻模式） | 只输出 `Waiting for Qdrant before claiming index tasks`，无限循环 | **任务永不被认领**，材料永远 `pending` |

两个阻塞的根因是同一个：**代码假设 Qdrant 与 embedding 一定存在**，而这台机器上两者都没有。
关键词路其实完全能用（降级重建后实测命中 1 条），但被两处上层逻辑挡在外面。

#### 阻塞 A：界面默认选了一个当前环境不支持的模式

`/knowledge` 的「检索方式」下拉框**默认选中的是「混合检索」**，而 `keyword` 排在第二项。也就是说——

> **试用者在 `/knowledge` 页输入一个词、直接点检索，必然拿到 503 的「检索服务暂不可用」红字。**
> 这不是他的操作问题，是默认值选了一个当前环境不支持的模式。

任务 3 会因此记成 `❌`，但扣的不是他的分。

#### 阻塞 B：常驻 worker 在没 Qdrant 时不会降级，而是死等

`index_worker.run()` 里那段等待没有出口：

```python
if not once:
    while True:
        try:
            qdrant(config).get_collections()
            break
        except Exception:
            LOG.info("Waiting for Qdrant before claiming index tasks")
            time.sleep(interval)
```

没有 Qdrant 就一直转圈，`process_one` 一次都不跑，所以那条「向量失败 → 重建关键词」的降级路径
根本轮不到执行。`--once` 模式因为跳过这段等待才跑出降级效果——**这恰好说明降级逻辑本身是好的，
被入口的等待挡死了**。

#### 补齐方式与结果

| 做法 | 内容 | 状态 |
| --- | --- | --- |
| **改代码（已采用）** | ① `/knowledge` 按 `RetrievalConfig` 的能力决定默认项：`embedding_ready` 为假时默认 `keyword`，`hybrid` / `vector` 置灰并注明「未配置向量服务」，`生成简短回答` 一并禁用；② `index_worker.run()` 在 `embedding_ready` 为假时不进入 Qdrant 等待，直接开始认领，让 `process_one` 走既有降级 | **已修复并实测** |
| 配齐 embedding + 起 Qdrant | 拿 `EMBEDDING_*`（硅基流动 bge-m3 / 通义 / 智谱），`docker compose up -d` | 未做，非必需 |

修复后的实测（同一套环境，仍无 Qdrant、无 `EMBEDDING_*`）：

| 检查 | 结果 |
| --- | --- |
| `/knowledge` 下拉框 | 首项 `<option value="keyword">关键词</option>`，`hybrid` / `vector` 带 `disabled` 与「未配置向量服务」 |
| 页面提示 | 出现「当前环境未配置向量服务……**关键词检索不受影响**，已默认选中」 |
| `生成简短回答` 按钮 | 带 `disabled` 与 `title="未配置模型服务，暂不可用"` |
| 上传材料 | 201，`material_id=4` |
| 索引（常驻 worker，非 `--once`） | 日志打出 `Embedding not configured; claiming tasks without waiting for Qdrant`，2s 时 `pending` → **6s 时 `ready`**，job 记 `failed / ModelUnavailable`（预期，向量建不出来） |
| 学生关键词检索 | **200，命中 1 条，正是刚上传那篇** |
| 复测材料清理 | 204，`status=deleted` |

> 判定：降级链路现在从「上传」到「学生搜到」整条通了，且**试用者不需要知道任何模式名字**——
> 页面首项就是能用的那个。`hybrid` / `vector` 仍然如实返回 503（不静默降级），
> 只是界面不再把它们作为默认值推给人。

> 另：`trial_start.py` 只起 web，不带 worker。试用时仍需另起一个
> `python -m campusclaw.index_worker`（现在它会正常认领，不会再死等 Qdrant）。
