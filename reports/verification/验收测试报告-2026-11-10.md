## 四、五个关键验收样例逐项实证

### 样例① A 班学生发帖后仅 A 班可见 —— 通过

学生 `student_a1`（A 班）发帖后，B 班教师 `teacher_b` 与学生 `student_b1` 分别以 GET 详情、GET 列表、POST 回复三种方式尝试触达，**全部 404，B 班列表为 0 条**。班级范围由服务端从会话恢复，请求体里没有任何 `class_id` 入参可用。

### 样例② 同学与教师可回复、学生不能采纳 —— 通过

- 教师 `teacher_a` 回复学生帖 → 201，问题状态由 `OPEN` 转 `ANSWERED`；
- 学生 `student_a1` 回复教师帖 → 201（证明"同学"侧同样可回复）；
- 学生调用 `POST /api/qa/questions/{id}/accept` → **403 `ROLE_FORBIDDEN`**，学生无法伪造教师采纳；
- 教师采纳后 → 200，`status=ACCEPTED`，`accepted_reply_id` 精确指向被采纳的那条回复（`reply_id=1`）。

### 样例③ FAQ 发布后本班检索命中且来源可追溯 —— 通过

| 步骤 | 实测 |
| --- | --- |
| 教师发布 FAQ | 201，`faq_id=1` |
| FAQ 沉淀为真实材料 | 生成 1 份材料，`material_id=3`，标题「本班 FAQ 汇总（自动生成）」 |
| 本班关键词检索 | 命中 1 条，`material_id=3`，标题正确 |
| 来源字段完整性 | 命中结果含 `chunk_id`、`chunk_index`、`start_offset`、`end_offset`、`offset_basis`、`material_id`、`material_url`、`excerpt`、`score`、`source_mode` |

来源可追溯这一条做得比选题报告要求更细：不仅能指到材料，还能指到**具体切片与字符区间**，引用链接可以直接跳到 `/api/materials/3`。

需要说明一个实现选择：FAQ 并没有"一条 FAQ 一份材料"，而是**把全班已发布 FAQ 汇总成一份 `faq.md` 材料**再走标准索引链路。这是为了不改动检索层（`knowledge_chunks.material_id` 非空外键、`material_index` 一材料一条、引用链接固定 `/api/materials/{id}`）。好处是零检索代码改动，代价是粒度变粗——命中只能定位到汇总材料，靠切片区间再细分。

### 样例④ 重复发布不产生重复知识条目 —— 通过

| 检查 | 期望 | 实测 |
| --- | --- | --- |
| 同一问题重复发布 FAQ | 409 `QA_FAQ_EXISTS` | 409 `QA_FAQ_EXISTS` |
| 活跃 FAQ 材料数 | 1 份 | 1 份 |
| 知识正文条数 | 1 条 | 1 条 |
| 编辑 FAQ 是否新建材料 | `faq_material_id` 不变 | 仍为 `3` |
| 编辑 FAQ 是否新增知识条目 | 仍 1 条 | 1 条 |

去重靠两道闸：业务层 `qa_faqs` 对 `question_id` 的唯一约束，数据层 `qa_faq_materials.class_id` 单行映射 + `knowledge_entries.material_id` 唯一。编辑走 `UPDATE` 而非 `INSERT`。

### 样例⑤ 索引失败保留材料与记录、恢复后可重建 —— 部分通过

**前半段（保留）全部通过：**

| 检查 | 实测 |
| --- | --- |
| FAQ 变更后入队索引任务 | 有 `queued` 任务（`material_id=3`） |
| 零模型下 worker 执行 | `Index task 4 failed: ModelUnavailable`，`material_index.status=failed` |
| 材料是否保留 | 材料仍 `active`，正文 182 字符未丢 |
| 未索引内容是否谎称可检索 | 检索 0 命中——如实反映"未就绪"，符合选题报告"不把未成功索引的内容假称为已可检索" |
| 既有 FAQ 是否被牵连 | 第一条 FAQ 仍可命中（世代 1 的 ready 切片未失效） |

**后半段（恢复）不通过**（其中「显式重建接口」一项为 44 项用例集之外的补充探测，用于确认恢复路径是否真的存在）：

| 检查 | 期望 | 实测 |
| --- | --- | --- |
| 重启后自动重建索引 | `status` 回到 `ready` | 仍为 `failed`，`active_generation=1` |
| 恢复后第二条 FAQ 可检索 | 命中 ≥ 1 条 | 0 条 |
| 显式调用重建接口 `POST /api/materials/3/reindex` | 202 入队，执行后回到可检索 | 202 入队（`job_id=5`），worker 再次 `ModelUnavailable`，新增第三代 3 条 failed 切片，仍 0 命中 |

需要区分两件事：**重建入口是有的**（`POST /api/materials/{id}/reindex`，教师可调用，返回 202），问题在于这条路和首次索引走的是同一条强依赖嵌入的链路，在未配置嵌入模型的环境下必然再次失败；而启动补建这条"不依赖模型"的兜底路径，又被上一轮留下的 failed 切片挡住了。两条路同时断，才导致样例⑤后半段不成立。详见 DEF-01。

## 五、数据库一致性检查（8/8 通过）

验收不只比对接口返回值，直接查库核对"服务端说的话"和"库里的事实"是否一致。

| 检查项 | 口径 | 结果 |
| --- | --- | --- |
| 回复无孤儿记录 | `qa_replies.question_id` 全部能在 `qa_questions` 找到 | 0 条孤儿 |
| 采纳关系指向本问题的回复 | `accepted_reply_id` 对应回复的 `question_id` 必须等于该问题 id | 0 条错配 |
| `ACCEPTED` 必有采纳记录 | 状态与字段不矛盾 | 0 条矛盾 |
| 知识正文与材料班级一致 | `knowledge_entries.class_id == materials.class_id` | 0 条跨班错配 |
| 检索切片与材料班级一致 | `knowledge_chunks.class_id == materials.class_id` | 0 条跨班切片 |
| FAQ 发布人属于本班 | `qa_faqs.class_id == users.class_id` | 0 条跨班发布 |

## 七、缺陷记录

### DEF-01【中】【已确认】零模型环境下索引失败后无法恢复，重建入口也救不回来

**现象**

在未配置任何模型的环境下，只要索引 worker 处理过某份材料并失败，这份材料此后检索不到；重启应用不会自愈；教师调用重建接口虽然返回 202，执行后仍然失败，且每重建一次就多留一代 failed 切片。

**复现步骤**

1. 不配置 `EMBEDDING_*`，启动应用（`start-all` 会同时拉起 index worker）；
2. 教师发布一条 FAQ（或上传一份材料）；
3. worker 处理该材料，报 `ModelUnavailable`；
4. 再发一条 FAQ，触发材料重建与新世代切片；
5. 观察：`material_index.status = failed`，第二条 FAQ 检索 0 命中；
6. 重启应用，等待启动补建完成；
7. 观察：状态仍为 `failed`，第二条 FAQ 依然 0 命中；
8. 教师调用 `POST /api/materials/3/reindex` → 202 `job_id=5`；再跑 worker → 再次 `ModelUnavailable`，`active_generation` 仍是 1，第二条 FAQ 仍 0 命中。

**数据库现场**

```
material_index:  material_id=3  active_generation=1  status=failed  last_error=ModelUnavailable
knowledge_chunks: material_id=3  generation=1  index_status=ready   n=1
knowledge_chunks: material_id=3  generation=2  index_status=failed  n=3
knowledge_chunks: material_id=3  generation=3  index_status=failed  n=3   ← 调用 reindex 之后新增
index_jobs:      id=3 done / id=4 failed (attempts=1) / id=5 failed (reindex 触发)
knowledge_entries: material_id=3  正文 182 字符，"第二条FAQ答案正文" 位于第 90 字符
```

正文在、材料在、任务记录在，唯独检索不可用；而且失败世代会随重建次数累积，没有任何清理。

**根因**

三处共同造成：

1. `campusclaw/index_worker.py` 第 135-160 行：先插入 `pending` 切片，再调用嵌入。嵌入失败后异常处理把这些切片标成 `failed`，**但不删除**，于是每失败一次就留下 3 条 `index_status=failed` 的空壳切片。
2. `campusclaw/tutor_db.py` 第 281-293 行 `backfill_keyword_ready()`：启动补建的判定条件是

   ```sql
   AND NOT EXISTS (SELECT 1 FROM knowledge_chunks c WHERE c.material_id = m.id)
   ```

   **只要该材料存在任意一条切片（无论 ready 还是 failed）就跳过补建**。第二代那 3 条 failed 切片恰好挡住了唯一的"不依赖模型"的自愈路径。该函数也只覆盖"从未建过切片"的材料，不处理"建过但失败"的材料。
3. `campusclaw/views/retrieval_views.py` 第 84 行的 `reindex_api`：重建只是重新入队，走的仍是同一条 `worker → 嵌入 → Qdrant` 链路，没有"只重建关键词索引"的降级策略。所以在没有嵌入模型的环境里，教师点多少次重建都是同样的失败。

**影响**

- 直接违反关键验收样例⑤的后半句"恢复后可重建"；
- 教师侧：FAQ 改一次、失败一次，之后对全班学生不可检索；教师能看到 `failed` 状态，也有重建按钮的接口，但按下仍然失败，无法区分是模型没配还是数据坏了；
- 演示侧：按 `start-all` 一键启动（会拉起 worker）且用零模型演示时，第二条 FAQ 之后的内容就查不到了——这正好落在选题报告的核心演示动线上；
- 与选题报告 3.4 的承诺"向量服务失败时保留素材并显示索引状态"相比，"保留"和"显示"都兑现了，"允许教师重建索引"（3.2 节）只兑现了入口，没兑现效果。

**修复建议**（三选二，推荐第一 + 第三）

1. **让补建认失败态**：把 `tutor_db.py:288` 的 `NOT EXISTS` 收窄为只认 `ready`：

   ```sql
   AND NOT EXISTS (
       SELECT 1 FROM knowledge_chunks c
       WHERE c.material_id = m.id AND c.index_status = 'ready'
   )
   ```

   同时在补建前清掉该材料的 `failed` 切片，避免与旧世代数据叠加。
2. **失败即清理**：`index_worker.py` 的失败处理里删除本次插入的 `inserted_ids`，让材料回到"从未建过切片"的初始态，补建逻辑无需改动。
3. **给重建加关键词降级**：`reindex` 接受 `strategy` 时增加一个不走嵌入的 keyword-only 选项（或在嵌入式重建失败后自动回落到关键词重建），这样"模型没配/向量服务挂了"时教师点重建仍能把关键词检索救回来。

**优先级**：中。不阻断主链路演示，但阻断"索引失败后继续维护 FAQ"这一教师日常操作，且与规约承诺不符。

## 八、实现与选题报告规约的一致性核对

验收角色的职责之一是核对"做的"和"写的"是否一致。以下几处不一致，建议在规约文档（肖文睿侧）同步修订，否则评审时容易被质疑。

| 规约项 | 选题报告 | 实际实现 | 判定 |
| --- | --- | --- | --- |
| 技术栈 | React + TypeScript + Vite、Go API、MySQL、Qdrant、Docker Compose | Python 3.11 + Flask 3.1 + SQLite/FTS5 + Jinja 服务端页面；Qdrant 可选 | **不一致**，需更新规约。仓库 README 第 42 行已自述"Go/React/MySQL 规划，不是当前架构" |
| FAQ 发布接口 | `POST /api/qa/questions/{id}/faq` | `POST /api/qa/faqs`（另有 `faq-draft`、`PUT`、`DELETE`、`republish`） | 能力等价，路径不同，需同步接口文档 |

## 十、复跑方式

```bash
cd D:\campus-claw

# 1. 验收用例（44 项：正常/失败/越权 + 五个关键样例 + 数据库一致性）
.venv\Scripts\python.exe reports\verification\scripts\acceptance.py

# 2. 页面可用性（匿名 302 / 登录 200）
.venv\Scripts\python.exe reports\verification\scripts\pages.py
```

两个脚本都会在仓库根目录自建 `.acc/` 作为隔离数据目录（每次运行前清空 `appdata`），不会污染项目 `data/`；结果分别写入 `.acc/acceptance-result.json` 与 `.acc/pages-result.json`，可删除。

依赖安装注意：`uv.lock` 把包源写死为清华镜像，换机器时 `uv sync --locked` 会因源不匹配直接失败，需先 `uv lock` 或在能连通该源的网络下执行。
