## 六、问题与风险清单

### P1【中等 · 可用性】零模型环境启动过 worker 后，新材料永久无法检索

**现象**：不做任何模型配置（不设 `EMBEDDING_*`）时，上传材料后运行一次 `python -m campusclaw.index_worker --once`，该材料的索引状态变为 `failed / ModelUnavailable`，此后：

- 关键词检索查不到该材料（0 命中）
- 重启应用**不会**补建（与 README「重启一次应用，启动时会补建关键词切片」的建议相悖）
- `POST /api/materials/{id}/reindex` 只会再次失败

**复现步骤**（已实测）：

```bash
# 1. 不配 EMBEDDING_*，启动应用与上传材料
uv run python app.py
# 2. 上传任意 .md，记下 material_id
# 3. 运行索引 worker
uv run python -m campusclaw.index_worker --once
# 4. 查状态 -> failed / ModelUnavailable
curl -H "Authorization: Bearer <token>" http://127.0.0.1:8080/api/materials/<id>/index-status
# 5. 重启应用后再次检索该材料关键词 -> 0 命中
```

**对照实验**（同一实例、同一数据库）：

| 材料 | 是否跑过 worker | 重启后状态 | 关键词可检索 |
| --- | --- | --- | --- |
| 材料 6 | 否（保持 pending） | `ready`，generation=1 | ✅ 命中 1 条 |
| 材料 3/4/5 | 是（失败） | `failed`，generation=0 | ❌ 0 命中 |

**根因**（定位到具体代码）：

1. `campusclaw/index_worker.py:141-163`：先在同一事务里把所有切片以 `index_status='pending'` 写入 `knowledge_chunks`，**再**调用嵌入服务。
2. 嵌入失败时走 `except` 分支 `_mark_failed(...)`，把该代次切片置为 `failed` 并写 `material_index.status='failed'`，**但不删除这些残留切片**（实测材料 3/4/5 各留 1 条 `index_status='failed'`、`generation=1` 的切片）。
3. `campusclaw/tutor_db.py:281-293` 的 `backfill_keyword_ready` 判定条件是
   `NOT EXISTS (SELECT 1 FROM knowledge_chunks WHERE c.material_id = m.id)`——
   **只要存在任何切片（哪怕是 failed 的空壳），就被认为"已建过索引"而跳过**。
4. 于是这条材料既没有 `ready` 切片，又永远不会被补建，检索层按 `active_generation` 过滤后自然 0 命中。

**影响面**：`start-all.ps1` / `docker compose` 都会拉起 worker。零模型环境下按"一键启动"走一遍，**之后所有新上传材料都检索不到**，且界面只显示"索引失败"，不提示恢复办法。课堂演示"老师上传讲义 → 学生提问 → 引用原文"这条主线会直接断掉。

**建议修复**（任选其一）：

- `backfill_keyword_ready` 的存在性判定改为只统计有效代次，例如
  `NOT EXISTS (SELECT 1 FROM knowledge_chunks c WHERE c.material_id = m.id AND c.index_status = 'ready')`；
- 或在 `_mark_failed` 时删除本次插入的切片，让材料回到"从未建切"状态，从而被启动补建覆盖。

**建议文档同步**：修正 README「不配置任何模型也能完整跑通」的表述，明确"新材料的关键词索引在零模型下依赖启动补建，且不要在该环境启动 worker"。

### P2【低 · 可移植性】`uv.lock` 写死镜像源，换环境 `uv sync --locked` 直接失败

**现象**：全新克隆后按 README 方式一执行第一步即报错：

```
$ uv sync --locked
Resolved 75 packages in 4.38s
error: The lockfile at `uv.lock` needs to be updated, but `--locked` was provided.
```

**根因**：`uv.lock` 中每个包的 `source` 都记录为 `https://mirrors.tuna.tsinghua.edu.cn/pypi/web/simple`，而使用者环境的默认索引不是清华源（官方 PyPI 或其它镜像），uv 认为锁文件与配置不一致。

**影响**：新同学按 README 第一条命令就会卡住；不知道可以去掉 `--locked` 的人会以为是环境坏了。

**建议**：README 补一句"若报 `lockfile needs to be updated`，先 `uv lock` 再 `uv sync`"；或生成的 lock 不绑定镜像源。

---

### P3【低】SEC-06 依赖漏洞基线未完成在线比对

项目 `check_security.py` 自述"本机未安装 pip-audit 且离线，无法给出高危/严重数量"。本次检测同样未联网核查依赖 CVE，因此**依赖安全等级未定**，不能视为"无漏洞"。建议联网环境补跑 `pip-audit`。

### P4【信息】内置演示凭据公开、严格模式默认关闭

4 个账号口令硬编码为公开值，且服务启动横幅会把口令打印到控制台。作者已在文档中明确"仅限本机演示、对外部署必须替换并开启 `CAMPUSCLAW_STRICT_CONFIG=1`"，本次实测严格模式确实能拒绝启动。属**已知设计取舍**，非缺陷，但部署到公网前必须处理。

## 九、总体评价

**做得好的部分**：

- 班级隔离是"服务端 404"级别，不是前端隐藏；跨班读材料、读问题、查任务、查索引状态四处抽查全部 404。
- 身份字段一律服务端取，请求体里塞 `class_id` / `role` 会被拒（异步接口实测 400）。
